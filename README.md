# ForgeHands

ForgeHands connects a git forge (**Forgejo**, **Gitea** or **GitLab**) to **OpenHands**. In **direct mode** it runs the whole loop from a labelled ticket to a merged pull request: it starts OpenHands conversations with the agent profile that belongs to a label, follows the pull request through CI, review, follow-up rounds and merge, keeps branches current, orders tickets by their dependencies and calls a human only when one is needed. In **webhook mode** (the original, simpler use) it only verifies, filters and re-signs Forgejo issue events for an OpenHands Automation custom webhook.

A small Node.js 26 service written in TypeScript (run by type stripping, no build step, no runtime dependencies).

> Status: in daily use, released as `v0.5.x`. Coming from `v0.3.x`? Read [docs/UPGRADING.md](docs/UPGRADING.md) first. Do not expose ForgeHands to the public Internet without TLS, network controls and monitoring.

In this document "pull request" also means a GitLab **merge request**, and "Forgejo" in a variable name (`FORGEJO_URL`, `FORGEJO_TOKEN`, `forgejo_token_secret`) is kept for compatibility and stands for the configured forge.

## How the loop works (direct mode)

1. A label on an issue starts a run with the agent profile of that label: `ai:plan` a **planner** (splits the ticket into sub-issues and sets their dependencies), `ai:ready` a **worker**, `ai:escalate` a worker on a stronger model. The names are yours; they are the keys of `LABEL_ROUTES`. An issue that depends on open issues waits until the last of them closes.
2. The worker opens a draft pull request from the branch `ai/issue-<n>` (title starts with `WIP:`, on GitLab `Draft:`).
3. The forge reports every finished CI run. A **red** commit starts a **fix round**; a **green** commit (all workflows) starts the **review**, and on protected paths also an advisory **security review**.
4. The reviewer gives its **verdict** for that commit, `Verdict: OK` or `Verdict: NOT OK` with evidence. Where the verdict lives depends on `VERDICT_SOURCE`:
   - `comment` (default): one comment, plus the label `ai:approved` or `ai:changes`.
   - `review`: the forge's **native review** (Approve or Request changes) from a user of its own, which branch protection can enforce and which can need several approvals (`REQUIRED_APPROVALS`).
   - `both`: either of the two.

   A request for changes (`ai:changes`, or a native rejection) starts the next **round** of the worker on the same branch.

5. An approval merges the pull request when the commit is green and **no changed file matches the repository's deny list** (`MERGE_POLICY`). Otherwise the pull request is handed to a human.
6. Rounds are limited by `MAX_ROUNDS`. A route can name a stronger profile with `escalate_to`: the **last round runs on that profile before a human is called**. Only after that, the pull request gets `ai:blocked` and a comment that mentions the human.
7. A human who does not answer is **reminded** (`REMIND_AFTER_DAYS`): blocked, protected-path and untouched pull requests get a comment with a mention, a few times, then a stale label.
8. When the last dependency of an epic closes, the epic is reviewed against the default branch and closed if its criteria are met. An epic that stays open goes back to the planner once (`EPIC_GAP_REPLAN`); a human is called only when it is still open after that (see [Epics that stay open after their review](#epics-that-stay-open-after-their-review)).

**Dependency bot pull requests** (Renovate and similar, `BOT_AUTHORS`) join the loop at step 3 without a worker: a green commit is reviewed, an approval merges through the same `MERGE_POLICY`.

Everything outside step 1 needs `FORGE_URL` and `FORGE_TOKEN` (or their `FORGEJO_*` names). A route per label, the limits and the policy live in ForgeHands' environment, never in the repository: an agent's pull request cannot loosen the rules it is held to. `DRY_RUN=1` lets you watch all of this without a single write.

## Run it

Prerequisites: Docker with the Compose plugin, or Node.js 26+.

GitHub Actions tests every push and pull request and publishes multi-platform images (`linux/amd64`, `linux/arm64`) to `ghcr.io/belphegorprime/forgehands` with the tags `latest` (the `master` branch), `vX.Y.Z` (a Git tag) and `sha-<full commit sha>`. Pin a version tag in production. The workflow is [`.github/workflows/ghcr.yml`](.github/workflows/ghcr.yml); it publishes with the scoped `GITHUB_TOKEN`, no personal access token is needed. A new package may start private: switch it to public in GitHub, Packages, ForgeHands, Package settings, or log in to the registry with a token that has `read:packages`.

```sh
cp .env.example .env          # webhook mode is active; uncomment the direct-mode block for direct mode
docker compose up -d          # pulls the published image, does not build
docker compose ps
curl -fsS http://127.0.0.1:8080/healthz
```

`compose.yaml` binds the port to `127.0.0.1`. To accept webhooks from another host, use a secured reverse proxy and an explicit network policy. To run without Docker: `npm start`. To build a local image: `docker build -t forgehands:local .` and `FORGEHANDS_IMAGE=forgehands:local docker compose up -d`. Keep registry and webhook secrets out of committed files. The data directory (`DATA_FILE`, `JOBS_FILE`) is a volume in `compose.yaml`; the ledger in it is what survives a restart. The ledger file says which format version it has. A ledger written by a newer ForgeHands stops the start of an older one with a message, instead of being read and saved with what the older one does not know dropped, so a rollback keeps the file intact. An entry that is not valid is left out on load, and the log says which one (`ledger: dropped an invalid entry of <collection> (<key>)`).

## Forge setup

### What works where

|                                           | Forgejo                                                  | Gitea                                                | GitLab                                                               |
| ----------------------------------------- | -------------------------------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------------- |
| Webhook path, check                       | `/webhooks/forgejo`, `X-Forgejo-Signature` (HMAC-SHA256) | `/webhooks/gitea`, `X-Gitea-Signature` (HMAC-SHA256) | `/webhooks/gitlab`, `X-Gitlab-Token` (the secret itself, **weaker**) |
| CI events                                 | `action_run_failure`, `action_run_success`               | `workflow_run` (Gitea 1.25+, Gitea Actions)          | `Pipeline Hook` of merge request pipelines                           |
| Native reviews (`VERDICT_SOURCE=review`)  | reviews API                                              | reviews API (same code path, see Gitea notes)        | verdict **note** plus **approval**                                   |
| Issue dependencies and epics              | yes                                                      | yes                                                  | needs **Premium** (issue links `blocks`)                             |
| CI events of dependency bot pull requests | yes                                                      | **no**                                               | yes, from the pipeline's user                                        |
| Branch update (`UPDATE_BRANCHES`)         | `POST /pulls/<n>/update?style=rebase`                    | the same                                             | `PUT .../rebase`, polled                                             |
| Merge                                     | `MERGE_METHOD`                                           | `MERGE_METHOD`                                       | `squash` or the project's own setting                                |
| Subgroup paths in `ALLOWED_REPOS`         | n/a                                                      | n/a                                                  | yes (`group/sub/project`)                                            |

All three need the same from you: a **user of its own** for ForgeHands and the agents, a **token**, a **webhook per allowed repository** with the events below, and the **labels** you route (`ai:plan`, `ai:ready`, `ai:escalate`, `ai:review`, `ai:changes`, `ai:approved`; `ai:blocked` is created when missing). Give that user write access to the allowed repositories and no administrator rights. Its token is `FORGE_TOKEN`; for the agent it is handed over as `FORGEJO_TOKEN` (see `AGENT_SECRETS`).

A minimal direct-mode setup, the same on every forge but for `FORGE`:

```sh
FORGE=forgejo                      # or gitea, gitlab
FORGE_URL=https://git.example.com
FORGE_TOKEN=...                    # the ForgeHands user's token
FORGE_WEBHOOK_SECRET=...           # at least 16 characters, the same as in the webhook
ALLOWED_REPOS=team/app
OPENHANDS_API_URL=http://openhands:8000
OPENHANDS_API_KEY=...
AGENT_SECRETS=FORGE_TOKEN,FORGE_URL
LABEL_ROUTES={"ai:ready": {"profile": "<worker profile uuid>", "tier": "free"}}
```

Add `MERGE_POLICY`, the review and CI routes and the rest from [Configuration](#configuration) when you want the loop beyond the first run. Try it with `DRY_RUN=1` first.

### Forgejo setup

Create a **Forgejo** webhook per allowed repository (Settings, Webhooks):

- URL `https://YOUR-HOST/webhooks/forgejo`, content type `application/json`, secret = the exact `FORGE_WEBHOOK_SECRET` (never an empty one).
- Events. Webhook mode: **Issues**. Direct mode: **Issues** (including label changes and closed), **Issue comment** (`issue_comment`, see [Comments and earlier work](#comments-and-earlier-work)), **Pull request label**, **Actions run failure** and **success** (`action_run_failure`, `action_run_success`) and **Push**. With `REVIEW_WITHOUT_CI` (the default) also **Pull request** events for opened and updated pull requests (the generic **Pull request** event covers them; the label event you already have is part of it). With `VERDICT_SOURCE=review` or `both` also **Pull request approved** and **Pull request rejected** (see [Reviewer accounts](#reviewer-accounts-native-reviews)). With the default `HUMAN_REVIEW_ROUNDS=1` and `VERDICT_SOURCE=comment` also **Pull request review approved**, **Pull request review rejected** and **Pull request review comment** (`pull_request_review_approved`, `pull_request_review_rejected`, `pull_request_review_comment`); only the reviews of `HUMAN_LOGIN` count there, and a request for changes of his starts a round (see [Follow-up rounds and escalation](#follow-up-rounds-and-escalation)).
- Forgejo may not deliver to an HTTPS URL whose certificate comes from a private CA; a plain internal `http://` URL works (the payload is HMAC-signed).

For a clean division of rights, the Forgejo user of ForgeHands is not a person: its token is `FORGE_TOKEN`, it has write access to the allowed repositories and it is not an administrator. It authors the agents' pull requests.

### Gitea setup

Set `FORGE=gitea` (with `FORGE_URL`, `FORGE_TOKEN` and `FORGE_WEBHOOK_SECRET`; the agent still gets its secrets as `FORGEJO_URL` and `FORGEJO_TOKEN`). Gitea shares Forgejo's API, so everything above applies; only the webhook differs. Create a **Gitea** webhook (type Gitea) per allowed repository:

- URL `https://YOUR-HOST/webhooks/gitea`, content type `application/json`, secret = the exact `FORGE_WEBHOOK_SECRET`. ForgeHands checks `X-Gitea-Signature` (hex HMAC-SHA256 of the body) and reads `X-Gitea-Event` and `X-Gitea-Delivery`; Forgejo's headers and `/webhooks/forgejo` are not accepted on a Gitea setup.
- Events: **Issues** (Gitea reports label changes as `issues` with action `label_updated`), **Issue comment** (`issue_comment`), **Pull request** and **Pull request label** (`pull_request`), **Workflow run** (`workflow_run`, Gitea 1.25 or newer, needs Gitea Actions) and **Push**. A finished `workflow_run` (`conclusion` `failure` or `success`) becomes the same internal event as Forgejo's `action_run_failure` and `action_run_success`; cancelled and skipped runs are ignored. With `VERDICT_SOURCE=review` or `both` also the review events (approved, rejected): Gitea's review events go through the same code as Forgejo's. With `HUMAN_REVIEW_ROUNDS` (comment mode) the review events of `HUMAN_LOGIN` are read the same way, the review comment event (`pull_request_review_comment`) included. Gitea documents them as `pull_request_review_approved` and `pull_request_review_rejected` (the umbrella `pull_request_review` delivers both and the comment event); the docs do not name the checkboxes of the webhook form, so pick the review entries of the pull request group.
- Verified against the Gitea source and webhook docs: merge (`Do`, `head_commit_id`), `POST /pulls/<n>/update?style=rebase` (409 on conflict), combined status, compare, pull files, issue dependencies and blocks, reviews, and the `WIP:` / `[WIP]` title prefixes (case-insensitive, and `mergeable` is false for them, as on Forgejo).

What does not work on Gitea:

- A dependency bot's pull request (`BOT_AUTHORS`) gets no review or fix round from CI: Gitea's `workflow_run` names the pull request only by number and branch, with no author. Label events of such a pull request still work.
- A CI event of a pull request carries no title or body; the agent reads the issue itself. Whether the pull request is still open is read from the API before a round starts.
- Only runs of a pull request or a push count, and a head branch in a fork never counts as an agent branch.
- Metrics count Gitea API errors under the `forgehands_forgejo_api_errors_total` series (one family).

### GitLab setup

Set `FORGE=gitlab` with `FORGE_URL` (the instance, for example `https://gitlab.example.com`), `FORGE_TOKEN` and `FORGE_WEBHOOK_SECRET` (the agent still gets its secrets as `FORGEJO_URL` and `FORGEJO_TOKEN`, and sends the token as `PRIVATE-TOKEN`). A pull request is a **merge request** everywhere, and its number is the `iid`. `ALLOWED_REPOS` takes the full project path, subgroups included (`group/sub/project`).

- **Token**: a personal, project or group access token with the `api` scope, for a user of its own with at least the Developer role (it comments, labels, rebases and merges), sent as `PRIVATE-TOKEN`.
- **Webhook** per allowed project (Settings, Webhooks): URL `https://YOUR-HOST/webhooks/gitlab`. On GitLab 19.0 and later use a **Signing token** and set `FORGE_WEBHOOK_SECRET` to it exactly (`whsec_...`), leaving the secret token empty. On an older GitLab use a **Secret token** = the exact `FORGE_WEBHOOK_SECRET`. Triggers: **Issues events**, **Merge request events**, **Pipeline events** and **Push events**. ForgeHands reads `X-Gitlab-Event` (`Issue Hook`, `Merge Request Hook`, `Pipeline Hook`, `Push Hook`) and uses the `Idempotency-Key` as the delivery id.
- **CI**: a finished pipeline (`status` `failed` or `success`) of a merge request becomes the same `ci.failure` / `ci.success` event as Forgejo's run events; cancelled, skipped and running ones are ignored. The combined status of a commit is derived from its pipelines (red wins, a running or manual one holds, a rerun replaces the older pipeline of the same source and ref). Use **merge request pipelines** (`rules: - if: $CI_PIPELINE_SOURCE == "merge_request_event"`): a plain branch pipeline names no merge request in the event.
- **Labels** are matched by name. GitLab's _scoped_ labels are those with a double colon (`a::b`): two of the same scope replace each other. The default labels (`ai:ready`, `ai:approved`, ...) have a single colon and are ordinary labels, so they do not replace each other; do not give your own labels a `::` unless that replacement is what you want.
- **Draft** replaces `WIP:`: the titles `Draft:`, `[Draft]` and `(Draft)` count, and ForgeHands removes the marker before it merges an approved, green merge request.
- **Rebase** (`UPDATE_BRANCHES`) is `PUT .../rebase`, which runs in the background: ForgeHands looks at the merge request until it finishes and reads a failed rebase (`merge_error`) as a conflict. **Merge** is `PUT .../merge` bound to the checked head with `sha`; `MERGE_METHOD=squash` asks for a squash, every other value is the project's own setting (merge commit, semi-linear or fast-forward), because GitLab has no such parameter.
- **Webhook security**: the format of `FORGE_WEBHOOK_SECRET` decides how a delivery is checked.
  - **A signing token** (`whsec_<base64>`, GitLab 19.0 and later, Standard Webhooks): every delivery must carry `webhook-signature`, an HMAC-SHA256 of `webhook-id`, `webhook-timestamp` and the raw body. It must also be at most five minutes old, so a copied delivery cannot be replayed later. `X-Gitlab-Token` is then ignored, so nothing can fall back to the weaker check. A `whsec_` value that does not decode to a key of at least 24 bytes stops the start.
  - **Any other value** is the secret token. GitLab sends it in clear in `X-Gitlab-Token`, and ForgeHands compares it in constant time, but it is **weaker than an HMAC**: a copy of one delivery (from a proxy log, say) lets anybody post any body. Keep the hop between GitLab and ForgeHands short and on TLS, restrict who can reach the port, and switch to a signing token when your GitLab has it.

What does not work, or differs, on GitLab:

- **Dependencies probably need Premium.** The links `blocks` / `is_blocked_by` are listed as Premium in GitLab's documentation of the MCP tools and quick actions; the issue links API page names no tier, so whether Free refuses them is not verified. When the call is refused or empty there are no dependencies: issues are not held back, `waiting for #n` and epic review by dependencies do nothing. Links into other projects are ignored.
- A dependency bot's merge request (`BOT_AUTHORS`) is recognised from the pipeline's user only: the merge request event does not name the author, so its label events (the approval) are ignored.
- Pipelines on a merged result run on a merge commit, not on the head of the merge request, and are dropped as stale. Use plain merge request pipelines.
- The event of a pipeline carries no merge request text; the agent reads it from the API. Issue events carry no comment count.
- **Native reviews** (`VERDICT_SOURCE=review` or `both`): GitLab's REST API has no review object and no "request changes". A review is a **note** that begins with `## Verdict: OK` or `## Verdict: NOT OK` and ends with `Commit: <sha>`, plus, for OK, the reviewer's **approval** (pinned with `sha`). ForgeHands reads the notes and the approvals: an OK counts only with the approval of its author, NOT OK is a request for changes, the newest note per reviewer wins, and the commit in the note must be the head (so an old approval does not survive a push). The agent prompt tells the reviewer to post exactly that. `approval` / `unapproval` events of the merge request trigger the check like Forgejo's review events (they come with **Merge request events**).
- The agent reads review comments from the merge request's discussions (`.../discussions`).
- Metrics count GitLab API errors under the `forgehands_forgejo_api_errors_total` series (one family).

## Reviewer accounts (native reviews)

With `VERDICT_SOURCE=comment` (the default) the reviewer agent works under the same user as everybody else and the verdict is a comment plus a label. With `review` or `both` the verdict is the forge's own review, and a forge refuses a review of one's own pull request: **each reviewer needs a user of its own**, different from the user behind `FORGE_TOKEN` that authors the pull requests. ForgeHands rejects a reviewer token that equals `FORGE_TOKEN` at start. This is what to set up, in order.

**1. A user per reviewer.** Create a forge user for the reviewer (for example `forgehands-reviewer`; a second reviewer is a second user). Give it write access to the allowed repositories as a collaborator or team member, because only an approval of someone who may approve counts: on Forgejo and Gitea ForgeHands accepts an approval only when the forge marks it `official`, which means write access and, with the approvals allowlist (Gitea: "Restrict approvals to allowlisted users or teams"), being on it. On GitLab give it at least the Developer role. Not an administrator.

**2. A token for it.** Create an access token for that user and put it in ForgeHands' environment under a name of your choice, for example `REVIEWER_TOKEN`. It has to read the repository and write pull request reviews (on Forgejo and Gitea the scopes `write:repository` for the review and `write:issue` for comments and labels; a token limited to specific repositories can carry only `read`/`write:repository` and `read`/`write:issue`; on GitLab the `api` scope). The Forgejo and Gitea documentation maps scopes to groups of routes, not to single endpoints, and GitLab names no narrower scope than `api` for approving and commenting, so these are the documented groups, not a tested minimum: if the first review fails with a 403, the call is logged and the run ends without a verdict.

**3. Hand it to the reviewer route only.** List the name in `AGENT_SECRETS` and refer to it from the review route with `forgejo_token_secret`:

```sh
REVIEWER_TOKEN=...                                   # the reviewer user's token
AGENT_SECRETS=FORGE_TOKEN,FORGE_URL,REVIEWER_TOKEN
VERDICT_SOURCE=review
LABEL_ROUTES={"ai:ready":   {"profile": "<worker uuid>",   "tier": "free"},
              "ai:changes": {"profile": "<worker uuid>",   "tier": "free", "on": "pull_request"},
              "ai:review":  {"profile": "<reviewer uuid>", "tier": "free", "on": "ci_success", "forgejo_token_secret": "REVIEWER_TOKEN"}}
```

The value of `REVIEWER_TOKEN` is handed to the conversations of that route only, as `FORGEJO_TOKEN`; no other conversation receives it, so the worker cannot approve its own pull request. Start fails with an error when the name is not an extra entry of `AGENT_SECRETS`, names `FORGE_TOKEN` or `FORGE_URL`, has the value of `FORGE_TOKEN`, sits on a route that is not `"on": "ci_success"`, or when `VERDICT_SOURCE=review` has a review route without it.

**4. A second reviewer (optional).** Add a second `"on": "ci_success"` route with its own profile, user and token, and set `REQUIRED_APPROVALS=2`. Each review route runs once per commit, in parallel:

```sh
REVIEWER_A_TOKEN=...
REVIEWER_B_TOKEN=...
AGENT_SECRETS=FORGE_TOKEN,FORGE_URL,REVIEWER_A_TOKEN,REVIEWER_B_TOKEN
REQUIRED_APPROVALS=2
# "ai:review-a": {..., "on": "ci_success", "forgejo_token_secret": "REVIEWER_A_TOKEN"},
# "ai:review-b": {..., "on": "ci_success", "forgejo_token_secret": "REVIEWER_B_TOKEN"}
```

**5. Subscribe to the review events.** Forgejo: webhook events **Pull request approved** and **Pull request rejected**. Gitea: the matching review events. GitLab: **Merge request events** (they carry `approval` and `unapproval`). ForgeHands acts on these events: an approval event asks for the merge and a rejection starts the next round, so without them the review is written but nothing reacts to it: the check after a review run only confirms that a review exists and leaves the merge or the next round to these events, and an approved pull request waits until some other event of it arrives.

**6. Branch protection** (Forgejo and Gitea: Settings, Branches, the default branch). It is the enforcement for humans and a second line for ForgeHands, which merges through the API:

- **Required approvals**: the same number as `REQUIRED_APPROVALS`. ForgeHands does not read it from the protection rule; keep the two equal.
- **Approvals allowlist**: Gitea calls it "Restrict approvals to allowlisted users or teams" (older Gitea releases said "whitelist"; Forgejo's documentation does not name the options and its settings page may still say "whitelist", so look for the matching entry there). Put the reviewer users (and the humans who may approve) on it. Without it every user with write access counts as an official reviewer; with it only the listed ones, and only their approvals are `official`, so only those count for ForgeHands too.
- **Dismiss stale approvals** (or, weaker, "Ignore stale approvals", which is not available while dismissing is on): on, so that a push takes the approvals back. ForgeHands ignores a review for any commit but the current head anyway.
- **Block merge on rejected reviews**: on, so that a request for changes also stops a human merge in the web interface.
- Make sure the user behind `FORGE_TOKEN` may merge under these rules (for example through the merge whitelist), otherwise a merge is refused by the forge and handed to a human.

On GitLab the split is by tier. Approving through the API (`POST .../approve`, pinned with `sha`) and reading approvals work on Free, and every user with at least the Developer role may approve, but there approvals are **optional**: GitLab does not block a merge without them, so ForgeHands' own count (`REQUIRED_APPROVALS`) is the only enforcement and a human can still merge in the web interface. Required approvals (rules with a number of approvers) and "Remove all approvals when commits are added to the source branch" are Premium or Ultimate; there, set the required number to `REQUIRED_APPROVALS`. By default the author of a merge request cannot approve it, so the reviewer must be another user in any case.

**7. `ALLOWED_SENDERS`.** If it is set, add the reviewer logins. A rejection starts a round of the worker, so the reviewer who rejects must be allowed to steer it. An approval needs no sender check: it only asks ForgeHands to read the reviews, which decide. A closed issue needs none either: whoever closes it, the epic review of its epic may start (see [Epics that stay open after their review](#epics-that-stay-open-after-their-review)).

How a review counts: per reviewer the latest review that is not dismissed, not stale and made for exactly the head commit; an approval needs a body of at least `MIN_REVIEW_CHARS` (evidence, not a click); the pull request is approved when `REQUIRED_APPROVALS` distinct users approve and nobody's current review requests changes. A human's approval in the web interface counts the same way, so write evidence there too.

**Migrating from comment to review mode.**

1. Create the reviewer user(s), tokens and the `AGENT_SECRETS` / `forgejo_token_secret` entries (steps 1 to 3). Subscribe the webhook events (5) and set the branch protection (6).
2. Set `VERDICT_SOURCE=both` first. A review route with a token now posts native reviews; one without keeps the comment and label. Either is accepted, a request for changes always wins, so nothing in flight breaks.
3. When every review route has its token, set `VERDICT_SOURCE=review`. From then on a label alone merges nothing.
4. To go back at any time, set `VERDICT_SOURCE=comment` (the default) and lower `REQUIRED_APPROVALS` to 1, which comment mode needs. The `forgejo_token_secret` fields stay valid: a review route keeps its own user, and the reviewer then writes a comment and sets the label again.

## OpenHands setup

**Direct mode.** Set `OPENHANDS_API_URL` (for example `http://openhands:8000`) and `OPENHANDS_API_KEY` (the backend key, `LOCAL_BACKEND_API_KEY` of Agent Canvas, not a model provider key). `LABEL_ROUTES` refers to agent profiles by their UUID (`GET /api/agent-profiles`).

**Webhook mode.** ForgeHands targets the **OpenHands Automation custom webhook** API of the Agent Canvas image (it bundles Canvas, Agent Server and Automation Server). Check that the API exists (401/403 means yes, 404 the wrong image or version): `curl -i http://127.0.0.1:8000/api/automation/v1/webhooks`. Register a source, ideally from the Canvas UI (Automate, Events) or a locally generated request so that secrets stay out of the shell history:

```sh
curl -X POST "$OPENHANDS_HOST/api/automation/v1/webhooks" \
  -H "X-Session-API-Key: $OPENHANDS_SESSION_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "ForgeHands Forgejo Issues", "source": "forgehands", "event_key_expr": "type",
       "signature_header": "X-Signature-256", "signature_scheme": "hmac_sha256_hex",
       "event_id_header": "X-ForgeHands-Delivery", "webhook_secret": "REPLACE_WITH_OPENHANDS_WEBHOOK_SECRET"}'
```

For OpenHands Cloud use `Authorization: Bearer $OPENHANDS_API_KEY`. Use the returned `webhook_url` as `OPENHANDS_WEBHOOK_URL` and configure an event automation for source `forgehands` and the keys `issues.labeled` and/or `issues.opened`. The agent prompts should treat issue text as untrusted input. In webhook mode ForgeHands holds no forge or LLM credentials and only the label `ai:ready` triggers a run; the outgoing payload is:

```json
{
  "type": "issues.labeled",
  "source": "forgejo",
  "action": "labeled",
  "repository": {
    "full_name": "team/app",
    "clone_url": "https://git.example/team/app.git",
    "html_url": null,
    "default_branch": "main"
  },
  "issue": {
    "number": 42,
    "title": "Add tests",
    "body": "Implement unit tests.",
    "html_url": null,
    "labels": ["ai:ready"]
  },
  "sender": { "login": "developer" },
  "delivery_id": "webhook-delivery-id"
}
```

Webhook mode follows `FORGE`: it listens on `/webhooks/forgejo`, `/webhooks/gitea` or `/webhooks/gitlab` and verifies the incoming webhook as that forge sends it (`X-Forgejo-Signature` or `X-Gitea-Signature`, HMAC SHA-256 over the raw body; on GitLab the secret token in `X-Gitlab-Token`, the signing token or the weaker secret token, see GitLab setup). The `source` of the outgoing payload is `forgejo`, `gitea` or `gitlab` accordingly. It allows only listed repositories, signs the outgoing body with a distinct secret in `X-Signature-256`, keeps processed delivery IDs for seven days and fails closed on a wrong signature, invalid JSON, an oversized payload or an unlisted repository.

## Behaviour in detail

### Labels and re-labelling

A label added to an existing issue arrives from the forge as an `issues` event with action `label_updated` that lists the current labels but not the added one. ForgeHands remembers the labels it last saw per issue (in the ledger, 30 days) and starts a run for a trigger label that is **new** compared with that. So `ai:escalate` works next to `ai:ready`, an issue can be run again by removing and re-adding its label, and unrelated labels are ignored. For an issue it has not seen it starts the first trigger label that never ran. The ledger keeps `repo#issue:label` to conversation id; the same label on an issue that still has a queued or running run starts no second one.

### Comments and earlier work

**A comment answers a planner without sub-issues.** A planner may finish with questions and no sub-issues (its prompt says so). A comment of `HUMAN_LOGIN` on such an issue is the answer, and the planner starts again. The rule: the newest run of a planner label is `done`, the issue is open and still carries that label, the planner run created no sub-issues (no dependency of the issue that was not there when that run started; the issues it blocks never hold an answer back), and no run of the issue is queued, waiting or running. Each planner run records its dependencies when it starts (`deps_before` on the job); a job from before that record counts the dependencies created after its run started, when the forge gives creation times, and every dependency otherwise. A planner label is `SPLIT_LABEL` or an `EPIC_LABEL` that has a route of kind `issue`; `ai:close` has no route and is none. The restart goes through the normal enqueue path (tiers, quota fallback, limits), and the run's message gets one line: "You are started again because the operator commented. Read ALL comments of the epic first; his answers are binding; do not ask a question that was answered; ask only what is still open." A comment of anybody else, of an agent or of ForgeHands starts nothing, and nothing happens when the forge cannot be read or when the dependency answer is not a list. Each comment answers at most once. `PLAN_ANSWER_RESTARTS` (default `5`, `0` off, at most `20`) caps the restarts per issue and label; then one notice on the issue, and no more runs. The restarts are counted apart from `COMMENT_RESTARTS`, which is unchanged. A comment that arrives while the planner still runs is not kept: it starts nothing, as before (the planner's answer comes first in its own run). The metric `forgehands_plan_answer_restarts_total` counts the restarts. An answer that starts nothing after a finished planner is logged as `<repo>#<n>: <login> commented, not restarting the plan: <reason>` and counted by `forgehands_comment_ignored_total{reason}` (`has_sub_issues`, `not_open`, `label_gone`, `links_unknown`, `issue_unreadable`, `plan_answers_used_up`). Forgejo only, as the comment restarts.

**A comment of the operator restarts a run that failed.** With `HUMAN_LOGIN` set, a comment that this login writes on an open issue starts the last run of that issue again when that run failed (any result: no delivery, iteration limit, error, stuck, timeout, paused) or was handed to him. The label of that run starts again exactly as if it had just been added: the same route, quota fallback, tier, dependency and same-files waits and the hourly limits apply. The new run reads the comment (its prompt names it as the reason). Only the latest run of the issue counts, no run of it may be queued, waiting or running, and the label must still be on the issue; a planner run (`SPLIT_LABEL`) counts like a worker run. Comments on pull requests, edited and deleted comments, and comments of anybody else (or of an agent or of ForgeHands) start nothing; with `ALLOWED_SENDERS` the author must be listed too. Each comment starts at most one run. `COMMENT_RESTARTS` (default 2, `0` switches the feature off) caps the restarts per issue and label: after that one comment on the issue says so, and no comment starts anything more. Forgejo and Gitea only; the webhook must send the **Issue comment** event.

The issue text goes into the first message between markers and is marked as untrusted. The message tells the agent to read the comments of the issue first (the event carries their count, not their text) and to look for a pull request from the branch `ai/issue-<n>`: an open one is continued on the same branch (reviews, review comments and the conversation are read and answered, no second pull request), a branch without a pull request is reused, a closed or merged one ends the run with a comment. Only `ALLOWED_SENDERS` (else the sender of the label) may steer the agent through comments and reviews; anyone else is context only. Every run has a clone directory of its own (`<workspace>/<owner>-<repo>-issue-<n>`, plus `-review-<sha8>`, `-fix-<sha8>`, `-round-<delivery>`, `-security-<sha8>`), so a review never clones into the worker's checkout. These directories are removed again once their runs are over, see [Cleaning the workspace](#cleaning-the-workspace).

### Follow-up rounds and escalation

A route with `"on": "pull_request"` (for example `"ai:changes": {"profile": "<worker uuid>", "tier": "free", "max_iterations": 120, "on": "pull_request"}`) fires when its label is put on the pull request of an agent issue (head branch `ai/issue-<n>`; others are ignored). The run belongs to issue `<n>`: it checks out the branch, reads reviews, the conversation and the issue comments, fixes, pushes to the **same** branch, comments and removes the label so that the next round can be asked for with it. Labels of a pull request are kept apart from those of the issue with the same number. In comment mode the verdict is a label because a forge refuses a formal review of one's own pull request when agent and human share an account; in review mode a native request for changes starts the round instead (see below).

**A request for changes of the operator starts a round (`HUMAN_REVIEW_ROUNDS`).** In comment mode the verdict is a label, so a formal review of `HUMAN_LOGIN` would do nothing on its own. With the default `HUMAN_REVIEW_ROUNDS=1` (it needs `HUMAN_LOGIN`) his **request for changes** on the head commit of an open agent pull request (`ai/issue-<n>`, or a dependency bot pull request where `BOT_FIX_ROUNDS` allows rounds) starts the changes round exactly as the `changes` label does: the same route, tiers, quota fallback, `escalate_to`, same-files waits and hourly limits. As his label does, the review starts the rounds of the pull request again and lifts `BLOCKED_LABEL`, and it takes `APPROVED_LABEL` off, because the approved commit is no longer accepted. One review starts one round: a review delivered again, and a second request on the same head while its round is queued or running, start nothing, and a review of an older commit is ignored. His **approval** or **comment** review starts nothing and merges nothing; the merge stays driven by the label and the verdict. The round's prompt tells the agent to read every review of his that is newer than the last round, and their inline review comments, since an earlier approval can carry the requests. The reviews of anybody else are ignored in comment mode, as before. With `VERDICT_SOURCE=review` or `both` the native review path handles the reviews, unchanged.

`MAX_ROUNDS` limits rounds per issue (fix rounds and conflict rounds count, reviews do not). When used up, ForgeHands starts nothing, comments and adds `BLOCKED_LABEL`. The check runs when a round is asked for, and also when the **last allowed round ends** with a NOT OK verdict on the head it left (no further event would ask for a round then, so the human is called at once); a head the last round pushed is judged by its own review. A pull request that is stuck in other ways is covered by [the watchdog](#stuck-pull-requests-the-watchdog). Whatever the human (`HUMAN_LOGIN`) does on such a pull request, setting a label or pushing a commit (its CI run names him), starts the rounds again and takes `BLOCKED_LABEL` off, whatever caused the block; agents' events never reset it. **Stopping a run:** remove its trigger label from the ticket (for a round, from the pull request), or close the ticket. A paused run whose label is gone or whose ticket is closed is not resumed; it ends as `failed` with result `paused`, and the log says why. Nothing else is written to the ticket, and it is not split or handed to a human. A pause alone, `POST /api/conversations/<id>/pause`, does not stop a run: ForgeHands resumes a paused run (`PAUSE_RESUMES`).

**Escalation: a stronger model before a human.** A round route (`pull_request`, `ci_failure`, `conflict`) or an issue route (no `on`) may name `"escalate_to": "<another route>"`, for example `"ai:changes": {"profile": "...", "on": "pull_request", "escalate_to": "ai:escalate"}`. On an issue route the escalation is the one for a worker that finishes twice without a delivery (see [Humans and failures](#humans-and-failures)); a round is escalated as described here. The last round (the `MAX_ROUNDS`-th, or from `ESCALATE_FROM_ROUND` on) then starts with the profile and tier of the target route, so a stronger model gets the last try before a human is called. Everything else stays: branch, kind, prompt, the iteration and budget limits of the own route, and it counts as a round. A round that is not escalated yet and still ends stuck, timed out or out of iterations is escalated as well, once per head commit (see [Humans and failures](#humans-and-failures)); that fresh run is not a round. The tier limits and cooldowns apply to the target's tier. The job records `escalated` and `/status` shows it. A human action that resets the rounds resets the escalation. The target's own `escalate_to` is not followed (no chains). Without `escalate_to` nothing changes. The target's profile is the operator's choice in `LABEL_ROUTES`; the label itself is not needed, so no one can trigger it from an issue. Point it only at a profile you trust for that repository: the last round runs with whatever the target profile may do.

### CI events: fix round and review

The forge sends one event per finished CI run. A commit starts at most one run per kind, however many workflows it has. A **red** commit starts a fix round (reproduce, fix, push to the same branch, comment). A **green** commit starts the **review**, only when the **combined commit status** is green, so a pending or failed second workflow holds it back. **A repository without CI** (`REVIEW_WITHOUT_CI`, default on) never sends a run event, so nothing would start. Instead the review starts on the new commit of an open agent pull request (`ai/issue-<n>`) or bot pull request (`BOT_AUTHORS`) when the commit has no commit status at all and its tree has no workflow file. ForgeHands reads that from the forge: the contents API at that commit, in Forgejo's own order `.forgejo/workflows`, `.gitea/workflows`, `.github/workflows` (the first folder that exists is the one that counts; only `.yml` and `.yaml` files in it do). The trigger is the push event (or the pull request opened or updated event, for a pull request opened after its branch was pushed). Then every `"on": "ci_success"` route starts once for that commit, exactly as for a green run (same key per commit, same security review for protected paths), and the log says `<repo>#<n>: no CI in <repo>, reviewing <sha7> without it`; the merge accepts such a commit as well. A repository that has workflows is unchanged: a red or pending commit, and a commit that has not reported yet, wait for the real run. If the forge cannot be read (an error, an answer that is no folder listing) nothing starts and the next event tries again; "no workflows" is remembered per repository and commit in memory only, "has workflows" never. The sender of an agent's commit must be in `ALLOWED_SENDERS` when it is set, as for a CI run. GitLab is not covered (a pipeline-less project cannot be told apart from one that has not started yet). A CI outcome starts nothing when the run was cancelled or skipped (Forgejo reports a replaced run as a failure; only `status: failure` counts), when its commit is no longer the head of the pull request, or when the commit has recovered meanwhile. While an agent still works on the issue the outcome is **kept, not dropped** (shown as "CI result kept") and judged when that run ends; a kept outcome older than `MAX_RUN_MINUTES` is dropped.

**The review sweep closes the gaps the events leave.** A review starts from a green commit (a webhook) or from a finished round. When that event is lost, deferred, or a round ends without a new commit, the head of an open agent or bot pull request can stay unreviewed for ever: nothing else would ever look at it. With `REVIEW_SWEEP_MINUTES` (default `10`, `0` = off) ForgeHands reads the open pull requests of each allowed repository and starts the review of a head that has **no job in the ledger for that commit** (in any state: a failed review is the retry logic's business), whose CI is green or absent, and which is not waiting, queued or running. A pull request with an approved, changes, blocked or hold label, a draft (the forge's mark, but not a `WIP:` title: an agent pull request keeps that title until it is merged, so it is swept), a head from a fork, or a pull request older than 30 days is left alone; so is a head whose CI is pending or failed. The review starts through the same path as a green webhook, so a late webhook for the same commit cannot start a second one. At most 5 reviews a pass, and each commit is tried at most once an hour. One line per start: `<repo>#<n>: head <sha7> has no review, starting it`; the counter `forgehands_review_sweep_starts_total`. A pass reads one page of 50 open pull requests per repository. The same pass is the approval safety net: an approved, green pull request with an OK verdict that is not merged is handed to the merger once per head and 30 minutes (see [Auto-merge](#auto-merge)); one line `<repo>#<n>: approved and green at head <sha7> but not merged, the approval sweep hands it to the merger`.

### Stuck pull requests (the watchdog)

**Nothing else ever looks at a pull request that stands still with a NOT OK verdict, or one that conflicts.** A round that pushes nothing, or the last round of `MAX_ROUNDS`, leaves its pull request where it is; no event follows. The watchdog runs in each review sweep pass (`REVIEW_SWEEP_MINUTES`) over the open agent pull requests of each allowed repository (`ai/issue-<n>`, and the revert pull requests `ai/revert-<n>`), and blocks one that is stuck, **once per head commit and reason**:

- **(a) rounds used up:** the follow-up rounds of the issue are used up (`MAX_ROUNDS`), and the head has a review verdict that does not approve it. Blocked at once.
- **(b) NOT OK and no movement:** the latest verdict on the head says NOT OK (or asks for changes), no run of the issue is waiting, queued or running, and that has been so for `STUCK_PR_MINUTES` (counted from when the watchdog first saw it). Reason `stuck_verdict`.
- **(c) a merge conflict and no movement:** Forgejo reports the pull request as not mergeable (`mergeable` false, the branch conflicts with the default branch), and no run of the issue or of the pull request is waiting, queued or running (a conflict round counts as one), for `STUCK_PR_MINUTES`. Reason `stuck_conflict`. This holds whatever the verdict: a conflicting pull request cannot be merged by anybody.

**Revert pull requests** (`ai/revert-<n>`, opened by REVERT_ON_RED) are watched by the same rules. Their runs are counted under their own key (`repo!pr<n>`, as for a bot pull request). The ticket is the original ticket of the merge they revert, taken from the revert ledger: the blocked record marks that ticket on the status page. Without a record there is no ticket, and nothing is marked.

**A WIP title is not a draft for the watchdog.** Forgejo's `draft` follows a `WIP:` title, and every agent pull request carries `WIP:` until it is merged. So a draft is skipped only when it has no WIP marker (the author's own draft); the watchdog and the sweep both watch a WIP-titled agent pull request.

**A WIP title is not a conflict either.** Forgejo reports `mergeable: false` for a pull request titled `WIP:` whatever its branch. The watchdog therefore counts `mergeable: false` as a conflict (reason (c)) only when the title is clean. A WIP-titled pull request with a NOT OK verdict is blocked as `stuck_verdict` with the verdict's reason, and is never told it conflicts. When the merger strips the marker from an approved pull request, Forgejo may still say `mergeable: false` for a moment: ForgeHands reads the pull request again up to four times, two seconds apart, and refuses as a conflict only a flag that stays false.

A pull request is not stuck while it waits for its CI or its first review (no verdict on its head yet), while a run is queued or running on its issue, or while it carries the approval or the hold label. What it does is the same as a round that ran out: `BLOCKED_LABEL`, one comment that names the reason and quotes the first lines of the last verdict and mentions `HUMAN_LOGIN`, and the notification of kind `blocked` (`NOTIFY_IMMEDIATE`). It does not start a round or a review. When the human removes `BLOCKED_LABEL`, the pull request is eligible again after the grace of `STUCK_PR_MINUTES`, counted from the removal; a new head starts its own grace. Records of pull requests that are closed or merged are dropped.

The blocked pull requests are kept in the ledger (`stuck`). The tickets that wait behind one, directly or through other waiting tickets (an explicit dependency or a same-files wait), show `waiting behind stuck #<n>` as their state on `/status` and `/status.json`, with `blocked_by_stuck: [<n>]`; the idle line counts them as `<k> behind a blocked pull request`, and the gauge `forgehands_stuck_pull_requests` counts the blocked pull requests. The counter `forgehands_stuck_pr_blocks_total{reason}` counts the watchdog's blocks (`stuck_rounds`, `stuck_verdict`, `stuck_conflict`). `STUCK_PR_MINUTES=0` switches the watchdog off, and the chain marking with it; the last-round check above stays on. A dry run blocks nothing.

### Stalled tickets (the ticket watchdog)

The stuck-PR watchdog watches pull requests. A ticket can stall without one: its last run ended (done or failed) without a pull request, without a comment that delivers, and the ticket is still open, so nothing starts again and nothing tells anybody. The ticket watchdog (`TICKET_STALL_MINUTES`, default `180`, `0` = off) runs in the same review sweep pass and looks at each open ticket on an issue route that is stalled in this sense: its last run ended `TICKET_STALL_MINUTES` ago or more, no open agent pull request from `ai/issue-<n>` exists, no run of the ticket waits, is queued or runs, and it carries neither `BLOCKED_LABEL` nor `HOLD_LABEL`. Epics and planner tickets are left to the epic-gap path. A ticket that the end-to-end suite created (`E2E_REPO`, see `docs/e2e.md`) is left alone as well, while the suite runs and after it: the suite judges its outcome itself.

- **The first stall** starts the ticket once more: on the `escalate_to` route of its route when there is one, else on its own route. The run's message says that the last run ended without a delivery and asks it to deliver this time. Metric `forgehands_stalled_ticket_actions_total{action="restart"}`.
- **The second stall** (the restarted run ended the same way) calls the human, like a pull request that is handed over: a comment with a mention, `BLOCKED_LABEL`, a notification of kind `blocked`, and the ticket is listed in `waiting_for_human` with reason `stalled_ticket`. The tickets that wait behind it, directly or through other waiting tickets, show `waiting behind stalled #<n>` on `/status`. Metric `action="human"`, and the gauge `forgehands_stalled_tickets`.
- **Once per run.** A ticket is acted on once per last run; its record in the ledger (`stalled`) goes when the ticket is no longer stalled (a pull request exists, the ticket is closed). When the human takes `BLOCKED_LABEL` off, the ticket is looked at afresh: it is started once more if it is still stalled.
- **A start that does not happen** (the enqueue is refused or fails) goes to the human at once.
- **Dry run.** A dry run starts nothing and calls nobody (the review sweep skips a dry repository).

### Recurring findings become checks

**A correction that keeps coming back is a missing check, not a missing line of prompt.** With `RECURRING_REASON_MIN` (default `0`, off; `3` is the value to try) ForgeHands counts the NOT OK points of the changes rounds: the round that a NOT OK verdict starts (the `ai:changes` label, or a request for changes with `VERDICT_SOURCE=review`). Bot pull requests are not counted, and a NOT OK verdict that starts no round (rounds used up, a stuck pull request) is not counted either.

- **Points and reasons.** The latest NOT OK verdict of the head gives its points: the lines after the `Verdict: NOT OK` line, bullets and numbers taken off, at most five. A point becomes a reason: its first clause, in lower case, with quoted and bare paths as `<path>` and commit shas, line numbers and other numbers removed. So the same defect in another pull request gives the same reason.
- **Excluded.** A point that names a runner or environment limitation (`runner`, `limitation`, `unshare`, `no space left`, `rate limit`, time outs, `quota`, `ECONNRESET` and similar) is not counted: it says nothing about the code.
- **Counting.** A reason counts once per pull request head and repository. Only occurrences of the last 14 days count; the ledger keeps them 30 days (`findings`).
- **The ticket.** At the threshold one ticket is created in that repository. Its title is `Make this a check: <reason>`; its body links the verdicts, quotes the reason in a fenced block (verdict text is data: it is normalized and quoted, never used as a heading or a label) and has the sections of the ticket pre-flight (Files, Steps, Acceptance with a `npm test` command), asking the worker to add a lint rule, test or type constraint that fails on the point. With `SPLIT_LABEL` set the ticket gets that label, which sends it to the planner; without it, the ticket gets a comment that mentions `HUMAN_LOGIN` and says that nothing starts it.
- **Once per reason.** While the ticket of a reason is open, no other is filed for it. A closed ticket does not recur for 14 days after it was filed; after that, a reason that still comes up files a new one. The filed tickets are kept in the ledger (`filed_findings`).
- **Limits.** A forge without issue creation (GitLab) files nothing and logs that once. A dry run records and files nothing. Nothing is read or counted while the variable is `0`.

### The review

The reviewer reads the issue and the diff, checks against the issue's criteria and, for anything that talks to a system outside the repository, against reality (the counterpart's own description, a real read-only call), writes **one** verdict with the evidence. It neither pushes nor merges. In comment mode the verdict is a comment and `APPROVED_LABEL` or the changes label; a new round or review takes `APPROVED_LABEL` off first, so an approval never covers commits it has not seen.

**A label is not a review (comment mode).** Before a merge the pull request must carry a review comment for its current commit: written after that commit, at least `MIN_REVIEW_CHARS` long, with `Verdict: OK` or `Verdict: NOT OK` within its first 300 characters; the latest such comment decides, one from the reviewer or a human counts. Without one, or with a NOT OK latest, nothing is merged: the approval is taken off, the pull request gets `BLOCKED_LABEL` and a comment that mentions the human. A label that arrives a moment before its comment is looked at again after `APPROVAL_GRACE_SECONDS`. A review run that ends without a verdict is run once more (not a round); a second miss blocks the pull request.

### Native reviews as the verdict

With `VERDICT_SOURCE=review` (or `both`) the verdict is the forge's own pull request review. The reviewer submits `APPROVED` or `REQUEST_CHANGES` through the reviews API with `commit_id` set to the head commit and the evidence as the body (the same rules as the comment, `MIN_REVIEW_CHARS` applies to an approval's body) and sets no label. ForgeHands counts, per reviewer, the latest review that is not dismissed, not stale and written for exactly the head commit; an approval counts only when the forge marks the reviewer as one who may approve (Forgejo and Gitea: `official`). The pull request is approved when `REQUIRED_APPROVALS` distinct users approve and nobody's current review requests changes (a request for changes wins). The review events replace the label as the trigger: an approval asks for the merge, a rejection starts the next round of the worker (and the reviewer must be in `ALLOWED_SENDERS` if that is set; the rejection is checked against the reviews first). `both` accepts either a native review or a verdict comment with the label, but a current request for changes always wins; if the reviews cannot be read, `both` falls back to the comment. A route's reviewer prompt asks for a native review in `review`, and in `both` only for a route that has its own `forgejo_token_secret`.

A reviewer needs a user of its own, because the author of a pull request cannot approve it: see [Reviewer accounts](#reviewer-accounts-native-reviews) for the setup, branch protection and the migration. Limits: `REQUIRED_APPROVALS` is an environment variable only and is not read from branch protection; with several reviewers ForgeHands can tell that a verdict exists but not which reviewer is missing; reminders (`REMIND_AFTER_DAYS`) still look for the approval label only, so a pull request approved by native reviews alone is not reminded as "approved on a protected path".

### Checks from the forge

ForgeHands does not run the repository's checks. It reads their result from the forge: the commit status of the pull request head (`CHECKS_FROM_CI`, default `1`). Before a review run starts, the status of the exact head sha is read and given to the reviewer in its prompt as a block marked `ForgeHands check facts`:

- `CI state`: `success` (every check reports and passed), `failure` (a check failed), `pending` (CI exists and has not reported yet), `none` (no check reports and the repository has no workflow file at that commit), or `unknown` (the forge could not say).
- `Checks reported` and `Failed checks`: the names of the checks as the forge gives them (Forgejo and Gitea: the workflow and job, the context of the status). A forge that only gives the combined state gives no names. Names are cut at 80 characters and cannot close the block.

The block is data recorded by ForgeHands, not the reviewer's own finding. The reviewer does not re-run the CI or re-derive the result, and a command that cannot run on the runner (a container build that needs privileges the runner lacks, for example) is written as `not verified: runner limitation`, which is never a reason for NOT OK on its own.

Where ForgeHands judges a verdict (the merge gate and every check of whether a head is reviewed), a verdict is not accepted while the recorded state of its head is `failure`: the pull request is refused as a red CI (`ci_not_green`), and a native approval or a verdict comment does not count. A `pending`, `unknown` or `none` state does not change the verdict by itself; `none` is reported once per repository, see below.

**A repository without CI.** A head with no check and no workflow file is reported once per repository and process to the human, with the hint that revert-on-red (`REVERT_ON_RED`) and verification cannot work without CI. The message is kind `checks`: it is sent when `NOTIFY_IMMEDIATE` names `checks` and a channel exists, and it is always written to the log. The review is not held back (`REVIEW_WITHOUT_CI` decides that). With `REVIEW_WITHOUT_CI=0` the workflow folder is not looked up, so the state is `unknown` and no notice is sent.

**The switch.** `CHECKS_FROM_CI=0` leaves the prompts as they were (no facts block) and accepts verdicts whatever the forge's status says. GitLab reports the combined state only, so its facts have no check names.

**Declaring a check (next step, not implemented).** A repository will be able to name the command that its checks run, in a file `.forgehands.yaml` in its root, read through the forge API at the head sha:

```yaml
# .forgehands.yaml (planned format; ForgeHands does not read it yet)
check:
  command: npm run typecheck && npm test   # what the repository's check runs
  timeout_minutes: 15                      # a run that takes longer is a failure of the runner, not of the pull request
```

Running that command is a separate decision (where it runs, with which secrets, and how its output is recorded); until then the check result is the forge's.

### Auto-merge

`MERGE_POLICY` (JSON, per repository) lets ForgeHands merge the pull request of an agent issue once it is approved (`APPROVED_LABEL` with a verdict comment, or enough native approvals): `{"owner/repo": {"deny": ["stacks/**", "compose.yaml"]}}`. It merges only when the pull request is open, from `ai/issue-<n>`, not blocked, mergeable, the combined status of its head commit is green (or the repository has no workflow file at all, see `REVIEW_WITHOUT_CI`) and **none of its changed files (renames count with both names) matches a deny pattern**. Patterns: `*` within a folder, `**` across folders, a plain name is an exact path. The merge uses `MERGE_METHOD`, is bound to the checked head commit, deletes the branch and closes the issue. A pull request on a protected path is left to a human, with **one** comment that mentions him and says what is done (commit approved, CI green), why a human (each matching pattern with its reason, see below, and the files), what the security review found and whether the forge reports a conflict. When a security review of that commit is still under way, the hand-over waits for it and is written when that run ends. Approved and green ends the work in progress, so the `WIP:` marker is removed first, because the forge would not let the human merge it. A reason per pattern is optional: `{"owner/repo": {"deny": ["infra/**"], "reasons": {"infra/**": "decides what is reachable from the internet"}}}`. The policy lives in ForgeHands' environment on purpose: a policy file in the repository could be changed by the very pull request it should restrain.

**Every decision after an approval is logged.** Each time the approval of a pull request is looked at (the `ai:approved` label, a review, the end of a review run, the approval safety net below) and the pull request is not merged, ForgeHands writes one line `<repo>#<pr>: not merged: <reason>`, the reason being the one of the refusal (`not_approved`, `changes_requested`, `awaiting_approvals`, `awaiting_review`, `blocked`, `no_valid_review`, `ci_not_green`, `not_mergeable`, `protected_paths`, `awaiting_security_review`, `held`, `held_label`, `daily_limit`, `merge_failed`, `not_open`, `not_an_agent_branch`, `no_merge_policy`, `already_approved`, `duplicate_job`, `round_started`, `sender_not_allowed`). A merge writes `<repo>#<pr>: merged (<sha7>)`, the head commit it merged. The same refusal for the same head commit is written once an hour, not on every look. The counter `forgehands_merge_decisions_total{result,reason}` counts every decision (`result` `merged` or `not_merged`), and `/status.json` shows the last decision of each open pull request as `merge_decision: {reason, at}` on its ticket (the status page shows it after the state). A label change that adds `APPROVED_LABEL` is the approval even when a round label such as `ai:changes` is still on the pull request (a leftover of an earlier round): that round label used to hide the approval, and nothing then merged the pull request.

**The approval safety net.** The review sweep (`REVIEW_SWEEP_MINUTES`) also looks at the open agent and bot pull requests that carry `APPROVED_LABEL`, have an OK verdict for their head and green CI, and are not merged. Each such head is handed to the merger once every 30 minutes, so a lost or early webhook cannot strand an approved pull request. It never merges a pull request with `BLOCKED_LABEL` or `HOLD_LABEL`, a pull request under a two-key hold in the ledger, a draft, or one that touches a protected path (the dispatcher hands those over). It needs the sweep on and a `MERGE_POLICY` for the repository.

**Two keys** (`two_keys`, optional per repository) let a pull request that touches only selected protected paths merge without a human, when an independent second review agrees: `{"owner/repo": {"deny": ["seed/infra/ingress-controller/**"], "two_keys": ["seed/infra/ingress-controller/tests/**", "seed/infra/ingress-controller/README.md"]}}`. A list of globs (same syntax as `deny`), each of which must be covered by a deny pattern (a `two_keys` pattern that no deny pattern can match, or `two_keys` without `deny`, is a configuration error). When **every** changed file that matches the deny list also matches a `two_keys` pattern, the reviewer approved, CI is green and the [security review](#security-review-for-protected-paths-advisory) comment of that very commit says `OK`, ForgeHands merges as for an unprotected pull request and says so in its merge comment. With `CONCERNS`, without a security review, or while it is still running (the merge waits for it and happens when it ends with `OK`), the usual hand-over applies; one deny file outside `two_keys` keeps the human, and the hand-over names the files that would have qualified. Without a route `"on": "sensitive_review"` `two_keys` never merges anything. **The second key must be unforgeable by the author of the pull request.** Only a security review comment written by a login named in `SECURITY_REVIEWERS` counts (required with `two_keys`, otherwise ForgeHands does not start); a comment of anybody else, the worker included, is ignored, and the latest comment of the reviewer decides. `two_keys` therefore also needs `forgejo_token_secret` on every `sensitive_review` route (ForgeHands does not start without it): the security reviewer is a forge user of its own, whose token (an extra entry of `AGENT_SECRETS`) goes to that route's conversations only, as `FORGEJO_TOKEN`, so that the worker, which holds the agent token, cannot sign as the security reviewer. Give that user read access to the repositories and a token with the scopes `read:repository` and `write:issue` (to comment); it needs no write access. The policy lives in ForgeHands' environment: the pull request, its agent and the repository cannot add a pattern, only the operator can.

**A merged agent pull request closes its ticket.** After every push to the default branch ForgeHands closes the tickets whose agent pull request was merged into it (also by someone else, with a comment); the usual closed event then starts what waits for it.

### Safety nets for merges without a human

Three switches act on the merges ForgeHands makes without a human. All of them are off or neutral until set. They apply to the two-key merges (a pull request whose protected paths are all covered by `two_keys`) and, for the revert, to any merge ForgeHands made.

**The hold (`TWO_KEYS_HOLD_MINUTES`, `HOLD_LABEL`).** When both keys agreed and everything else holds, the merge waits. The pull request gets one comment, `ForgeHands: approved by both keys. It merges at HH:MM UTC unless the label `ai:hold` is put on this pull request or a new commit arrives.` (mentioning the human as the other comments to him do), and the status page shows `held until HH:MM UTC`. The hold is kept in the ledger, so a restart neither loses nor shortens it. The dispatch tick looks at a held pull request every five minutes; when the hold has ended it reads the whole review again for the current commit (the reviewer's verdict, the security review of that commit, CI, mergeable, `HOLD_LABEL` off, the policy) and merges only if all of it still holds. A new commit clears the hold, and the review of the new commit starts over. While `HOLD_LABEL` is on, nothing merges, two keys or not: the label stops every merge ForgeHands would make (refusal reason `held_label`). When it comes off, a full hold period starts, with its own comment, so the operator always gets the whole time.

**The daily limit (`TWO_KEYS_DAILY_LIMIT`).** A repository may merge at most this many pull requests through two keys in any 24 hours. The count comes from the ledger (every merge ForgeHands makes is recorded with its commit and whether two keys merged it; the ledger keeps 30 days). A pull request over the limit is not merged: it gets the usual hand-over comment with the reason `daily limit of N merges through two keys reached`, and the human is called as for any protected path. The limit is checked again when a hold ends.

**Revert on red (`REVERT_ON_RED`, `REVERT_WINDOW_MINUTES`).** After a merge ForgeHands reads the merge commit from the pull request (Forgejo's merge call does not return it) and records it. A failed CI run of a push to the default branch whose commit is such a merge, within the window, does three things, once per commit: it comments on the merged pull request, it tells the human at once (the `failed` notice), and, when a route with `"on": "main_red"` exists, it starts a run. That run creates `ai/revert-<n>` from the default branch, runs `git revert -m 1 <commit>` (or reverts the squash commit), runs the fast checks, and opens the pull request `WIP: Revert: <title>`. It does not fix forward; a revert that cannot be done is said on the original pull request. Example route:

**A failure that was already there is not reverted, and a flaky one gets a rerun.** Before a revert, the red check is compared with the commit before the merge (the first parent, read from the forge's git commit). The check counts as this merge's doing only when it was **green** on the first parent. A check that was red there too, or is not reported there, is pre-existing: the merged pull request gets one comment that says so (no revert is started, the human gets a `failed` notice with the reason, and the merge is marked `pre_existing` in the ledger). That is not a revert cause and does not count in the revert rate. When the check was green before the merge and is red after it, ForgeHands **reruns the failed run once** (`POST /actions/runs/{id}/rerun`, the run id from the event) and waits for it without blocking: the run is read again at each dispatch pass, and `RERUN_TIMEOUT_MINUTES` (default `30`, `0` = no rerun) is how long it may take. A rerun that passes ends it with no revert and no comment. A rerun that fails, does not finish in time, or cannot be started (the forge refuses it, or the event has no run id) reverts as before; the revert's comment then says what the rerun did. The rerun is recorded once per commit (in the ledger, 30 days), so a redelivery does not rerun again. When the first parent cannot be read, nothing is reverted and the human is called on the merged pull request. The decision never relies on the job log.

```json
{"main:red": {"profile": "<agent profile uuid>", "tier": "strong", "max_iterations": 60, "on": "main_red"}}
```

Without a `main_red` route the human is called on the merged pull request instead, and no run starts. A failed run of a revert is only reported to the human: there is no revert of a revert. The revert pull request is an ordinary agent pull request, but it has no ticket: like a dependency bot's pull request it is reviewed and merged under the merge policy, a red CI run of it is handled as a bot's (`BOT_FIX_ROUNDS` decides whether a worker fixes it), and it skips the hold and the daily limit. Only the Forgejo run event is read for the revert: Gitea and GitLab do not send it to ForgeHands yet.

**After the revert: reopen, explain, start again (`REVERT_RETRIES`, default 1, `0` = off).** A revert of an agent's merge is a fix of the default branch, but its ticket stays closed and its work is gone. When `ai/revert-<n>` is merged (by ForgeHands or by a human; it is seen on the push to the default branch that merged it, so `UPDATE_BRANCHES` must not be `0`), and the original pull request belonged to an agent ticket `ai/issue-<m>`, ForgeHands does four things, once each: it **reopens** ticket `m`, comments on it **once** with the cause (`> `-quoted, the first 1200 characters of the revert pull request's body, redacted: configured secrets, `password=`/`token=` pairs and long tokens are replaced; the revert run was told to write that text there), and starts the ticket's worker route again, the way a newly added label does, with one added line in its message that says its earlier change broke the CI and was reverted. The count is kept in the ledger per ticket (30 days): while fewer than `REVERT_RETRIES` restarts were made, the ticket is started again; then it gets `BLOCKED_LABEL`, a comment that mentions the human (`HUMAN_MENTION`), and a notice, and nothing restarts. The original ticket is not closed again by the pushes that follow. A bot's or a ticketless pull request is never touched. A step that fails (the reopen, the comment, the restart) is logged and tried again on the next push. Two pushes that handle the same revert at once still do the steps once: the second one waits out the first. Forgejo reports a merged pull request whose head branch was deleted with the head ref `refs/pull/<n>/head`; the branch names above are therefore read from the head label when the ref is that form. A revert whose record is missing (it was never kept) is recorded again from the ledger's merge of the original pull request, when that merge was of an agent's branch. **Reopening re-blocks the tickets that depend on it:** a ticket that waits for a reopened one waits again, which is correct, because they must wait for the repaired work.

**The revert rate (`REVERT_RATE_ALERT`, `REVERT_RATE_MIN_MERGES`).** The question behind it: how often was an autonomous merge wrong? Per repository, over the merges of the last 30 days, it is `reverted / merges`:

- A **merge** is a merge ForgeHands made (`recordMerge`, the merge ledger, kept 30 days), including dependency bot merges. The merges of revert pull requests (`ai/revert-<n>`) are not merges here.
- A merge is **reverted** when a revert pull request for it, `ai/revert-<n>`, was seen **merged** into the default branch (on the push that merged it, see the revert above). A revert that is only started, or that is open, does not count. A merge is counted **once**, however many merged revert pull requests name it, and a revert of a revert does not count the merge a second time.
- A merge **needed a human** when a red default branch after it was not undone by a revert of ForgeHands: there is no `main_red` route, the revert itself turned the default branch red, or the ticket was blocked after its revert (`BLOCKED_LABEL`). That is counted apart (`needed_human` in the summary, `forgehands_reverts_needing_human_total`); a merge can be both reverted and needed a human.
- The window is 30 days from the time of the merge; a merge older than that leaves the figure.

The metric `forgehands_merges_reverted_ratio{repository}` is that share from 0 to 1, written at scrape time from the ledger, and absent while the repository has no merge in the window (no division by zero). The status page and `/status.json` show the same figures per repository in the summary (`revert_rate: {merges, reverted, needed_human, ratio}`, `ratio` null without merges), for the 7-day window too, which is only a view; the rate the alert uses is the 30-day one.

`REVERT_RATE_ALERT` (a percentage, `0` by default: off) turns the figure into a notice: when a repository's rate is **above** it (equal is not above) and at least `REVERT_RATE_MIN_MERGES` (default 10) merges are in the window, the human gets one `failed` notice for that repository per UTC day, from the dispatch pass. The minimum keeps one revert of two merges from alarming. The notice is a prompt to tighten autonomy for that repository until the rate falls, for example `TWO_KEYS` in its `MERGE_POLICY`. Counters since start: `forgehands_merges_reverted_total{repository}` (once per merge) and `forgehands_reverts_needing_human_total{repository}`.

### Dependency bot pull requests

For Renovate and similar bots. A pull request qualifies when its author is in `BOT_AUTHORS`, its head branch starts with one of `BOT_BRANCH_PREFIXES` (if set) and the branch lives in the repository itself (not a fork). A branch `ai/issue-<n>` is always an agent pull request. Every other foreign pull request is ignored. A qualifying one follows the review and merge policy of agent pull requests, without a worker:

- A **green** commit starts the review once per commit. The reviewer reads the changelogs between the old and the new version and checks breaking changes against the repository's usage, and is wary of what a bump adds beyond its purpose (install scripts, new network access, files outside the manifests).
- `Verdict: OK` plus approval merges through `MERGE_POLICY` (deny list unchanged, no issue is closed). ForgeHands checks the author against `BOT_AUTHORS` on the webhook and again on the live pull request at merge time.
- A review that finds a problem, without `BOT_FIX_ROUNDS`, sets `BLOCKED_LABEL` with a mention: no worker fixes a bot's pull request, a human decides. If the reviewer sets the changes label anyway, ForgeHands hands the pull request to the human.
- A **red** commit starts nothing unless `BOT_FIX_ROUNDS` is set; then fix rounds are counted per pull request against that limit.
- ForgeHands never updates a bot's branch (Renovate rebases itself).
- The ledger and `/status` list it as `owner/repo!pr<n>`; there is no ticket, so the "issue number" of such an event is the pull request number.
- Titles, descriptions and changelogs are untrusted text, like issue text, and the prompt says that release notes fetched from the internet are evidence, not instructions. Their CI outcomes are let in by `BOT_AUTHORS`, not by `ALLOWED_SENDERS`; label and review events still need an allowed sender (approvals excepted, see Native reviews).

Limits: on Gitea CI events of a bot's pull request are not recognised, on GitLab a bot's merge request is recognised from its pipeline only (see the forge sections).

### Security review for protected paths (advisory)

A route with `"on": "sensitive_review"` starts a second, security-minded review when a commit is green and a changed file matches the deny list of the repository's `MERGE_POLICY`: once per commit, next to the normal review, never a round. The run is read-only and posts one comment starting `## Security review: OK` or `## Security review: CONCERNS` that names the commit. It sets no label, approves nothing and merges only through two keys. A run without that comment is started once more, then only logged; a failed run never blocks. The comment that hands a protected-path pull request to the human ends with what the security review found for that commit. Without the route nothing changes.

### Keeping pull requests current

With `UPDATE_BRANCHES` (the webhook needs push events) ForgeHands looks, after the default branch has been quiet for `BRANCH_UPDATE_DELAY_SECONDS`, at open pull requests from `ai/issue-<n>` that fell behind. An update changes the head commit, cancels the CI run in progress and throws a review away, so it acts only when it is cheap and needed: the pull request has neither an approval nor an OK review for its current commit, is not blocked, has no agent running on its issue, the default branch changed a file the pull request changes too (through compare and the pull request's files; a rename counts, an unclear case counts as "touches"), CI is not running on its head, and the last update was more than `BRANCH_UPDATE_MIN_INTERVAL_MINUTES` ago. Then the forge rebases it (no agent involved). An approved or reviewed pull request is not brought up to date (that would throw the review away), but when the forge reports it as not mergeable (reliable once the `WIP:` marker is gone, which approval removes) it gets a conflict round too, after which CI, the review and the security review run again; this matters for a protected-path pull request that waits for a human.

### Tickets on the same files

With `WAIT_FOR_SAME_FILES=1` a ticket that lists its files under a heading `## Exact files` in its body (bullet lines such as ``- `src/a.ts` ``, a trailing note like `(new)` is ignored; `dir/**` and `*` patterns are allowed) does not start while an older ticket works on the same files, because two such tickets end in conflicts and rebase loops. Just before a worker starts, ForgeHands compares the declared files with the files of the open agent pull requests (`ai/issue-<m>`, at most 20 looked at) and with the declared files of other open issues that have a queued, running or waiting job. A match is an equal path or a glob that covers the other path. The job then waits (`waiting for #m (same files)` on `/status`, `waiting_for_files` in the ledger) and is looked at again after a push to the default branch, when a run ends and when an issue closes. Only the ticket with the higher number waits, so the oldest goes first and two tickets never wait for each other. A ticket without the section, a failing forge read or the switch off means no waiting.

A same-files wait is never taken when the older ticket already waits for this one, through explicit dependencies or other waits in force: that would be a cycle that nothing could break. The graph of the waits comes from the ledger's waiting jobs, and for an open ticket without a waiting job (an epic whose job is done, whose children it depends on) from its open dependencies in the forge: read at most 40 times a pass, each ticket cached for 10 minutes, a failed read counted as none (nothing is dropped on it). ForgeHands then skips that one edge, logs it once (`not waiting for #m (same files): #m is blocked by this ticket (cycle)`) and counts it in `forgehands_wait_cycles_broken_total`. Explicit dependencies are never skipped: a cycle made of them alone is reported as `dependency cycle` and counted as the idle reason `cycle` (see [Status page and metrics](#status-page-and-metrics)), and it alerts like a hold (`STALL_ALERT_MINUTES`); a human has to break it.

### A ticket sent to the planner

When an epic label (`EPIC_LABEL`, e.g. `ai:plan`) is put on an issue that already has an open agent pull request (`ai/issue-<n>`), ForgeHands comments on that pull request, closes it (the branch stays) and removes the queued or waiting jobs of the issue other than the planner's, so that the slices do not build the same thing a second time. A worker run that is already running is left alone. Without forge access nothing happens; with `DRY_RUN` it is only logged.

When the update reports a conflict (Forgejo and Gitea: HTTP 409) the branch **conflicts**: a route with `"on": "conflict"` starts a **conflict round**, once per tip of the default branch and counted against `MAX_ROUNDS`: rebase, resolve each conflict so that the purpose of the pull request stays and what the default branch brought in is kept, run the checks, push once with `--force-with-lease`, comment what was resolved. This is the only kind of run in which a rebase and a force push are allowed. Without a conflict route, or with the rounds used up, the pull request gets `BLOCKED_LABEL` and a mention. A pull request that was busy (an active run) when the default branch moved is looked at once when that run ends, so a conflict that arrived meanwhile is not forgotten. Forgejo reports `mergeable: false` for a pull request titled `WIP:` even without a conflict, so that field is not used; the update call is the test.

### A ticket is checked before a worker starts

With `TICKET_PREFLIGHT=1` (the default) an issue that starts a worker route (any route that is not a planner: not `SPLIT_LABEL`, not `EPIC_LABEL`) is checked before its run starts, at the enqueue, so a retried delivery or a comment that restarts the run is checked too. Planner runs, epics and pull requests are not checked. The ticket is read from its headings:

- `Steps`: the steps of the work.
- `Files` (or `Exact files`, the heading `WAIT_FOR_SAME_FILES` reads): the list of files, one bullet per file with the path in backticks; `(new)` on the line says that the ticket creates the file.
- `Acceptance`: the acceptance criteria, with a fenced block that holds the command the check runs.

A ticket that breaks a **blocking** rule starts no run. `TICKET_PREFLIGHT_BLOCK` says which rules block; its default is `2,3`. Every other finding is **advisory**: it never rejects the ticket, gets no comment and no label change, and the worker sees it (see [advisory findings](#advisory-findings-of-the-pre-flight)). The rules:

1. Every file named in `Steps` is listed in `Files`. A name is listed when `Files` has its path, or a bare name (`models.ts`) is the basename of a listed file, or a path is the end of a listed one (`targets/models.ts` for `src/targets/models.ts`). A name that is not listed is still no violation when it is a file of the default branch (the forge's contents API answers that, as for rule 4). **Advisory by default**; it blocks when `TICKET_PREFLIGHT_BLOCK` lists `1`.
2. `Acceptance` has a fenced block with a command (no section, no block, or an empty block breaks it). **Blocking.**
3. The command is not a placeholder (`...`, `<command>`, `TODO`) and its quotes close. A line that starts with `#` is a comment and is not read. **Not done: running the command on the default branch to see that it fails there.** That needs a checkout of the repository, which ForgeHands does not have, and a runner to run it in; until ForgeHands has one, the command is checked as text only. **Blocking.**
4. The files listed in `Files` exist on the default branch, unless the ticket says it creates them. The ticket says so when a line says `new`, or when `Steps` has a creating word (create, add, new, emit, write, generate, introduce, scaffold). The rule has two forms, and only the first can block:
   - **Cannot be worked at all**: no listed file exists on the default branch, and nothing says a file is created. The message names each missing file. It blocks only when `TICKET_PREFLIGHT_BLOCK` lists `4`; the default list does not.
   - **Weaker form, advisory only**: a listed file is missing, not marked `new`, while another listed file exists or `Steps` say that files are created. The planner's lists are mixed, and a created file is not always marked `new`. It never blocks.

   The read uses the forge's contents API (Forgejo and Gitea). On GitLab the check is not made, because ForgeHands has no file read for it there; the rule then does not apply.

A name in `Steps` is a file when it has a file extension of a repository (`ts`, `json`, `yaml`, `md`, ...) and is not code: `import.meta.url`, `process.env.X` or `Array.isArray` are code, `Node.js` is prose (a bare name must be all lower case or all capitals), `v1.2.3` and `users-3.1.yaml` carry a version number, and URLs (`https://...`, `forge.example/...`) are not paths. In a fenced block of `Steps` only a token with a slash counts. In `Files` a path is a code span or a bare word with a slash that ends in an extension (`src/a.ts`). A glob (`src/*.ts`) or a folder is not checked. A forge that cannot answer rule 4 (a failed read) does not break the ticket: that file is not checked, and the log says so.

The pre-flight is **skipped** for a ticket that was worked on before (a worker run of it in the ledger, done or failed) or whose pull request from the branch `ai/issue-<n>` is open: such a ticket was workable once, and its rounds follow their own rules. The skip is counted as `result="skipped"`. When the open pull requests cannot be read, the ticket is not rejected either. The rejection itself never closes a pull request. A rejected ticket gets the planner label, and the planner route closes the open pull request of the ticket (the epic route, `endOriginalPull`); so a ticket with an open pull request is never rejected in the first place.

#### Advisory findings of the pre-flight

An advisory finding does not reject the ticket. ForgeHands adds one line to the worker's prompt, before the ticket text, that begins `Pre-flight notes, not blockers:` and names each finding as a fact (for example "the Steps name `commands.ts`, which the Files list does not contain"), then asks the worker to stay within the Files list unless the step clearly needs it, and to say so in the pull request. At most six notes are named. The notes are built when the run starts, from the ticket text the run was queued with (the `Files` lists are read from the forge again then). A ticket with only advisory findings is not looked up on its open pull requests, and nothing is written to the forge for it.

`forgehands_preflight_total{result,rule}` counts the checks: `result="ok"` (rule `none`), `result="skipped"` (rule `none`), `result="rejected"` once per blocking rule a ticket breaks (rule `1` to `4`), and `result="advised"` once per rule that has an advisory finding (rule `1` to `4`).

The rejection comment names at most six blocking violations and then says `and N more`; advisory findings are not in it.

The ticket then goes back to the planner: the trigger label comes off and `SPLIT_LABEL` is set, with no mention. Without `SPLIT_LABEL` the trigger label comes off, `BLOCKED_LABEL` is set and the comment mentions `HUMAN_LOGIN`, and one notification goes out. The comment names each violated rule and is written **once per revision** of the ticket (a hash of its title and body): when the label is set again without an edit, the ticket is routed again but not commented again; an edit makes a new revision, which is checked and commented as well. The once-per-revision mark is kept in the ledger. A dry run (`DRY_RUN`) writes nothing and keeps no mark.

### Operator prerequisites

Some work needs something only a person can provide: a token or secret to create, a setting of the forge, the package registry or the CI runner, an access right, hardware, or a decision. An agent cannot do that with its own credentials, and a worker that tries ends without a delivery. So such an item is a ticket of its own, labelled `OPERATOR_LABEL` (default `needs:operator`), and the work that needs it depends on that ticket.

- **The planner lists them first.** Its prompt says so: before it splits a plan, it lists what the plan needs that an agent cannot do, and creates **one ticket per item**, titled `Operator: <what>`, with the operator label as its only label and a body that says what to do and how to verify it. It makes every worker ticket that needs the item depend on it (the forge's own dependencies).
- **A worker that finds such a need** does not retry. If no open operator ticket covers it, it creates one the same way, makes its own ticket depend on it, comments once and finishes.
- **ForgeHands starts no run on an operator ticket**, whatever route label it also carries. The first time it sees the ticket (a label event, or the worker's run that created it) it sends one notification of kind `handover` (subject "needs an operator"), and keeps the ticket until it is closed.
- **`/status.json` lists it** in `waiting_for_human` with `reason: "operator_prerequisite"` and the ticket's `title`, and `/status` shows it there as well.
- **A worker run that ends with an open operator ticket as a dependency waits** (status `waiting`, `waiting for #n`). It is not a hand-back and not a `no_delivery`: no comment of ForgeHands, no escalation, no second run. The dependent tickets start as usual once the operator ticket is closed (the dependency path of [Epics and the order of sub-issues](#epics-and-the-order-of-sub-issues)).
- **The ticket watchdog** ([stalled tickets](#stalled-tickets-the-ticket-watchdog)) does not touch a ticket that waits for an open operator ticket; its stall record, if it had one, goes.
- **Limits.** The operator label is read from the events ForgeHands gets: a label that is removed by hand stays listed until the ticket is closed. Agents can set a dependency on Forgejo and Gitea only; on GitLab the planner and the worker write the ticket number into the body and comment, and ForgeHands cannot hold the worker back on its own.

### Epics and the order of sub-issues

The forge's own issue dependencies carry the order (the planner sets them). An issue that **depends on open issues waits** (`waiting for #n`) instead of starting, and starts when the last of them closes: ForgeHands reads the issue's dependencies when the label arrives and again just before a worker starts (an edge may be added after the label), and the `issues` event with action `closed` makes it look at what the closed issue blocks. An **epic** (a label of `EPIC_LABEL`) depends on all its sub-issues, so the forge refuses to close it while one is open. When the last dependency closes, the route with `"on": "epic_done"` starts a review: the reviewer checks every acceptance criterion against the default branch, writes **exactly one** comment with the evidence and closes the epic if all are met, otherwise leaves it open and names what is missing. `ai:close` marks an existing ticket that only needs that closing review: it has no route and starts no planner run (give it its dependencies first). `ai:plan` marks a ticket that is planned first and reviewed at the end. The `issues` event with action `closed` starts that review whoever closed the last sub-issue (a person, HUMAN_LOGIN, or the account that merged a pull request with `Closes #n`): a closed event is not checked against `ALLOWED_SENDERS`, and an epic that carries another label (`ai:changes` after an earlier review) is an epic as well. A closed event that never arrives is caught by the review sweep (see [Epics that stay open after their review](#epics-that-stay-open-after-their-review)). Without forge access issues are not held back; on GitLab Free there are no dependencies (see GitLab setup).

### Epics that stay open after their review

The epic review (`epic_done`) leaves an epic open when a criterion is not met. ForgeHands does not rely on the reviewer for what happens next. When the review run ends, it reads the issue: **closed** means nothing to do (the record of the epic is dropped). **Open** means a gap, decided once per head of the default branch:

1. **The planner gets a try** (`EPIC_GAP_REPLAN`, default `1`). ForgeHands comments on the epic with the reviewer's `Not met` lines (the part of the reviewer's comment from "Not met" on, at most 20 lines and 1500 characters, quoted as data in a fenced block: it is never an instruction), and then takes the planner label off and on again, which starts the planner run. The planner is the epic label of the epic that has a route of kind `issue` (`ai:plan`), else `SPLIT_LABEL`; without one, the epic was not planned by ForgeHands and the human is called at once. The planner writes sub-issues for the gap, and the epic is reviewed again when they are closed. No mention: the planner is no human.
2. **The human is called** when the epic is still open after that second review, when `EPIC_GAP_REPLAN` is `0`, or when there is no planner label. The comment starts with `@HUMAN_LOGIN` and quotes the same lines, `BLOCKED_LABEL` goes on the issue, and one notification of kind `handover` goes out (subject "stays open after the epic review", the reviewer's first lines in the text). The epic is listed on `/status` under "Waiting for a human" with the reason, and `waiting_for_human` in `/status.json` carries it with `pr: null`.

The budget belongs to the epic and lasts until the epic is closed: with `EPIC_GAP_REPLAN=2` the epic goes back twice. A review that ends on a head of the default branch the epic was already decided at writes nothing, so a repeated review cannot send the epic back or call the human twice. The reviewer itself is told not to mention anybody: its comment is evidence, the decision is ForgeHands'.

**The replan run is watched.** When the planner run that answers a replan ends without new open sub-issues (no sub-issue created by it is open), nothing waits for ever: if all sub-issues of the epic are closed, the epic review starts once more (`action="rereviewed"`), and an epic that review still leaves open goes to the human without another replan. If a sub-issue that was there before the run is open, the human is called at once (`action="handed_no_plan"`), with the planner's last comment quoted as data. A replan that ended `EPIC_GAP_STALL_MINUTES` ago without such a decision is decided the same way by the dispatcher's tick, which also covers epics stuck before the upgrade; a re-review that ends without a decision is handed to the human after that time.

**The review sweep starts the epic review an event missed.** The review starts from the `issues` event that closes the last sub-issue. When that event is lost, or the sub-issue was closed in a way that event does not reach, the epic waited for ever and so did everything behind it. Every pass of the review sweep (`REVIEW_SWEEP_MINUTES`) looks at the open epics of each allowed repository: the tickets the ledger knows as epics (a run of an `EPIC_LABEL` or `SPLIT_LABEL` route, or of the `epic_done` route, or an epic record) and the open issues that carry `EPIC_LABEL` or `SPLIT_LABEL` (listed from the forge; a forge without such a list leaves out this part). An epic with **at least one sub-issue, all of them closed**, that has **no epic review queued, running or finished after the last of those closes**, gets its `epic_done` review started, once per default-branch head: the ledger keeps the head of the last start per epic (`epic_sweeps` in `jobs.json`), so a review that failed on a head is not tried again on that head, and a new head is. An epic with `BLOCKED_LABEL` or `HOLD_LABEL` is left to the human. At most 20 epics are read in a pass (the one looked at longest ago first) and 5 reviews are started. Not seen: an epic that carries neither label and that the ledger does not know, and a repository whose default branch no event has named yet. Dry run: nothing starts.

Until its review starts, or while it cannot (a dry run, a human's label), `/status` shows the epic as **`epic review pending`** and the tickets that wait for it as `waiting behind epic review pending #<n>`; `/status.json` lists the epics in `factory.epic_reviews` (with their links), and the Epic gaps card of Factory health shows them. A pending epic is one whose review is due and has not started: a review that is queued or running, or that is done since the last close, is not pending. The starts are counted by `forgehands_epic_sweep_starts_total`, and each start is one log line `<repo>#<n>: all <k> sub-issue(s) closed and no epic review since, starting it on head <sha7>`.

The tickets that wait for the epic (an explicit dependency, directly or through other waiting tickets) show `waiting behind epic with gaps #<n>` on `/status` and `/status.json`, with `blocked_by_epic_gaps: [<n>]`; a ticket that waits behind a blocked pull request shows `waiting behind stuck` instead. The decisions are kept in the ledger (`epic_gaps` in `jobs.json`), and `forgehands_epic_gaps_total{action}` counts them (`replanned`, `handed`). When the reviewer wrote no comment, the planner is asked to check the criteria itself. A failed write on the planner's try hands the epic to the human instead, so the epic is not lost. `DRY_RUN` writes nothing and keeps no record: the would-be writes are logged, as for any other write.

### Scheduling

Within a repository, work on a ticket that has begun (a round, a review, a CI fix, a conflict round, an epic review) goes before a new ticket, so that what was started gets finished; then the **oldest ticket (lowest issue number)** that can start now goes first, not the one queued first. Between repositories the starts are shared by `REPO_WEIGHTS` (default weight 1; a higher weight means more of them): weights 2, 1 and 5 give 2 of 8, 1 of 8 and 5 of 8 of the starts while all three have work. The repository with the fewest starts per unit of weight among the last 50 started runs goes first; one with nothing that can start gives its share to the others. `MAX_CONCURRENT`, `MAX_CONCURRENT_PER_TIER` and `MAX_RUNS_PER_HOUR` stay global.

### Humans and failures

**Mail only when a human is needed.** With `HUMAN_LOGIN=<login>` the comments that hand something to a human start with `@<login>`: a pull request approved and green on a protected path, a conflict, a failed merge, a pull request marked `BLOCKED_LABEL`, a failed run, and an epic that its review found open after the planner had its try (see [Epics that stay open after their review](#epics-that-stay-open-after-their-review)). Nothing else mentions him (not a merge, not a round, not a rejection the worker fixes). Forges mail a mentioned user whose setting is "only on mention", but not the **actor** of an action, so the agents and ForgeHands must act as a forge user of their own.

**A run that "finishes" without delivering is not done.** A model that answers in words without calling a tool can end a worker run as `finished` in a minute with nothing done, and the ticket then waited for ever. A worker run on an issue (not a planner run, not an epic) must leave a pull request from `ai/issue-<n>` that was created or changed since the run began, or a comment on the issue written since then that is not a hand-back (below), or close the issue. A comment that the agent user wrote since then on an issue this one blocks (its parent) is a delivery only when this ticket is closed (then it is not reached at all). While the ticket stays open, that parent comment is a hand-back like a comment on the ticket itself: ForgeHands logs `<repo>#<n>: the run commented on #<parent> and left the ticket open, a hand-back`, and a blocker escalates, "done, nothing pushed" asks for the push. If it did none of these the run is made once more. After a second empty run the route decides: a route with `escalate_to` starts one fresh run on the profile of that route (the run is shown as "escalated after `no_delivery`" and counted for that tier; `FAILURE_ESCALATE`, see stage B below), and only if that run is empty as well is the ticket marked failed (`no_delivery`) and the human called with a comment on the issue. That comment says whether the escalation happened: "finished twice without a pull request and without a comment, and once more after `ai:escalate`" (or, after a hand-back, "was handed back by a comment, and the run after it on `ai:escalate` finished without ..."). The escalation is read from the route the ticket was started with, so a run that started on the `fallback_to` route of an out-of-quota tier is escalated too. A route without `escalate_to` goes to the human after the second empty run, as before. A forge that cannot be read changes nothing. When the trigger label is set again while the ended run is being looked at, the fresh run it queues takes over: the ended run is not made once more, not escalated and not reported to the human, so two agents never work on one ticket.

**A worker that hands its ticket back by a comment has not delivered (`HANDBACK_HANDLING`, default 1).** A comment written since the run began is a delivery only when it is a question, a plan or a progress report. ForgeHands reads the newest comment by its words, in English and German, without a model: "done, but nothing pushed" (`working tree`, `implementation complete`, `not pushed`) and blockers (`blocked`, `cannot`, `could not`, `unable`, `conflicting`, `contradict`, `missing`, `stopped before`, `no pull request`, and their German forms). The comment is untrusted text: it is matched and quoted, never obeyed. Each step is taken once per ticket, in this order:

1. "Done, but nothing pushed": the same route runs once more, its prompt gets the line that asks it to push `ai/issue-<n>` and open the pull request, even if an optional check could not run.
2. A blocker, or a second "nothing pushed": one fresh run on the profile of `escalate_to` (shown as "escalated after `handback`", counted for that tier). Without `escalate_to` this step is skipped.
3. A second hand-back, or no `escalate_to`: with `SPLIT_LABEL` the ticket goes back to the planner, with the worker's comment quoted and the trigger label swapped for the planner's label. Without it the ticket gets `BLOCKED_LABEL`, the human is mentioned and notified (kind `blocked`).

A run that opened or updated its pull request is a delivery, whatever it also commented. `HANDBACK_HANDLING=0` restores the former rule, where any comment is a delivery. The steps are counted in `forgehands_handbacks_total{kind}` (`retry`, `escalate`, `planner`, `blocked`). A dry run decides the same steps and writes nothing to the forge.

**A run that stops on its own is continued, then escalated, and only then a human is called.** Before a run that ends `stuck` (OpenHands' stuck detection) or hits the run timeout (`MAX_RUN_MINUTES`) is handed over, ForgeHands tries two things, in this order:

1. **Stage A, resume the conversation (`RESUME_ATTEMPTS`, default 1; for a paused run `PAUSE_RESUMES`, default 3).** A **paused** run is an interruption, not a verdict on the ticket (an OpenHands restart pauses the runs that were going): it gets one neutral message instead ("the run was interrupted ... continue from where you stopped ... end with the finish tool"), on a budget of its own, for every kind of run. A paused run is never split. It is not resumed when its trigger label is gone or its ticket is closed (see **Stopping a run** under [Follow-up rounds and escalation](#follow-up-rounds-and-escalation)); when the budget is used up or the resume cannot start, it goes to the human. ForgeHands sends one message to the same conversation, which keeps its context: the run stopped as `<state>`, do not repeat what was done last, look at the current state of the branch and the checks, take a different approach and end with the finish tool and a short summary. Then the run is started again. A timed out run is paused first. The run timeout starts again for the continued run. The continuation is counted on the job (`resumes`, the status page says "resumed", `forgehands_resumes_total`); it is not a new run for `MAX_RUNS_PER_HOUR`. The message and the run are two calls: a run call that answers 409 (it runs already) is taken as started, one that answers 429 or fails is repeated on the next poll, and the message is never sent twice. A message that OpenHands refuses is not a resume, and the next stage decides.
2. **Stage B, a fresh run on the escalated profile (`FAILURE_ESCALATE`, default 1).** A round on a route with `escalate_to` that is still `stuck` or timed out after stage A starts once more on the profile and tier of that route, on the same pull request and branch, with the own route's prompt and limits. A round that reaches its iteration limit goes there at once: an iteration limit is not continued, because nothing in the OpenHands API raises the limit of a conversation. The fresh run happens once per head commit of the pull request, does not use up a `MAX_ROUNDS` round, and is shown as "escalated after `<state>`". Its own run can be continued too (stage A), but it is not escalated again.
3. **Stage C, the human,** as described below: the pull request is marked `BLOCKED_LABEL` and the human is mentioned, or, for an issue run, the planner takes the ticket through `SPLIT_LABEL`.

Issue runs have stage A, then the `SPLIT_LABEL` behaviour. Stage B does not apply to them as it is described above, but an issue run that finishes without a delivery twice is escalated once on the `escalate_to` route of its label (see [A run that "finishes" without delivering is not done](#humans-and-failures)) before the human is called. Planner, epic, review and security runs have stage A only. Quota holds, `ERROR_RETRIES`, the `no_delivery` re-run and `DRY_RUN` are unchanged. `RESUME_ATTEMPTS=0` and `FAILURE_ESCALATE=0` restore the former behaviour, where a stuck run went to the human at once. `PAUSE_RESUMES=0` turns the pause resume off; a paused run then goes to the human as any other failure (still never split).

**A run that ends badly is not forgotten.** A conversation that ends in `error` is started once more after a minute (`ERROR_RETRIES`); a second end is final and is reported: on a pull request with `BLOCKED_LABEL` and a mention, on an issue with a comment that mentions the human. A run that reached its **iteration limit** (OpenHands reports `MaxIterationsReached` as an error) is not run again: it ends as `max_iterations`, because the same run would end the same way. With `SPLIT_LABEL` a worker run on an issue that ran out of iterations or time (`max_iterations`, `stuck`, `timeout`) is not a case for the human: the ticket is probably too big, so the worker label comes off, `SPLIT_LABEL` goes on and the planner splits it. Planner and epic labels are never sent there.

**The model is out of quota, or no model is available.** An error that says no model could answer (`LLMServiceUnavailableError`, `BadGatewayError`, `LLMTimeoutError`: the gateway tried every model of the combination, for example one without credits and one not configured) is handled like a used-up quota, but with a pause that grows (1, 2, 4, 8, 16, then 30 minutes) because such a window may be over in a minute or last hours; it is given up after `QUOTA_GIVE_UP_HOURS`. When a run ends in `error` and its last events say it was a rate limit (the gateway mostly tells when the quota is back, `retry_after`), ForgeHands neither fails the job nor calls a human: it queues the job again and holds the whole `tier` of that route back until then (at least a minute, at most `QUOTA_HOLD_MAX_HOURS`; a reset time given only in words, such as "reset after 4h 12m" or "Resets in 2 days", counts too; 15 minutes when there is none). It gives the job up only when the quota has been out for `QUOTA_GIVE_UP_HOURS` in a row. The status page shows "model quota used up, ... tries again after HH:MM UTC". The hold lives in memory, so a restart means "try again now".

**Fallback route.** A route may name `"fallback_to": "<another route>"`. While the tier of the route is on a quota hold (see above) and the tier of the fallback route is not, a job of the route starts with the profile and tier of the fallback route instead of waiting, so work goes on with another model. Branch, kind, prompt and the iteration and budget limits stay those of the own route. For example `"ai:ready": {"profile": "<worker on cheap>", "tier": "cheap", "fallback_to": "ai:ready-free"}, "ai:ready-free": {"profile": "<worker on free>", "tier": "free"}`. The fallback route needs no label: nobody triggers it from an issue. Any kind of route may have a fallback, an escalated round falls back from the route it escalates to, and the fallback route must not have a `fallback_to` of its own (one hop). The tier limits apply to the fallback tier, and the job records `fell_back` (shown by `/status`). When a run of the fallback model ends in a rate limit too, that tier is held and the job is queued again; the next start decides afresh. Without a free fallback the job waits as before.

**A worker that explores without pushing is nudged (`NUDGE_AT_PERCENT`).** Measured on 60+ finished worker runs on issues: a run needed a median of 55 actions (p75 95, p90 132, the limit is 150). The 9 runs that hit the limit had a median of 174 actions, and 10 of those 12 limit-hit runs had pushed no branch and opened no pull request: they explored or looped. The size of the ticket does not predict it, so there is no split rule for it. Instead, when a worker run on an issue has used `NUDGE_AT_PERCENT` (default 65) of its route's `max_iterations` and the forge shows no branch `ai/issue-<n>`, ForgeHands sends the conversation one message: it has used N of M actions and has not pushed a branch; stop exploring, implement the smallest change that meets the acceptance check, push it to `ai/issue-<n>` and open the draft pull request, or, if something blocks it, comment the exact blocker on the issue and finish. The actions are counted with OpenHands' event count (action events only), at most once a minute, and not before the run is three minutes old. Once per conversation: a continued run keeps the flag, a new conversation (after an error) starts with its own. Rounds, reviews, the planner and epic runs are never nudged. A count, forge or OpenHands error means "not known yet": nothing is sent and the next look is a minute later. The message goes out in the background with `NUDGE_TIMEOUT_SECONDS` as its timeout, so the dispatch loop never waits for it. It carries a marker; a timeout does not tell whether OpenHands stored the message, so the recent events are searched for the marker first, and the message is sent again only when they do not hold it (once, then no more nudges for that run). A refusal (HTTP 409, 423, 429) is retried on the next look. The nudge is counted in `forgehands_nudges_total{kind}` and logged as `<key>: nudged at N/M actions, no branch yet`.

### Reminders

Humans forget pull requests that wait for them. With `REMIND_AFTER_DAYS=<n>` (off by default; needs `FORGE_URL`, `FORGE_TOKEN` and `HUMAN_LOGIN`) ForgeHands looks once a day, and once after a restart, at the open `ai/issue-<n>` pull requests of the allowed repositories (dependency bot pull requests only when marked `BLOCKED_LABEL`) and finds three kinds:

- marked `BLOCKED_LABEL`,
- approved and green on a protected path (left to the human),
- untouched: no run queued, running or waiting, and no activity for `n` days.

For each, if the last ForgeHands comment is at least `n` days old, it writes one comment that starts with `@HUMAN_LOGIN`, says why the pull request waits and since when, and counts (`ForgeHands: reminder i of k`). At most `REMIND_MAX` reminders per pull request; with the last one `STALE_LABEL` is added when set. A comment by `HUMAN_LOGIN` starts the count again and holds reminders back for `n` days; a human taking over also lifts `BLOCKED_LABEL`, which ends them. Waiting jobs whose dependencies are all closed (a lost close event) are started in the same pass instead of reminded. `/status` lists what waits for a human ("waiting for a human since <date>").

Design notes: the state lives in the forge's comments (reminders are recognised by their text), so nothing new is stored and a restart only empties the `/status` list until the next pass. A pass reads one pull request list per repository, examines at most 20 agent pull requests per repository and writes at most 10 reminders. The text is built from fixed strings, label names and dates, never from issue or pull request text, and only `HUMAN_LOGIN` is ever mentioned. The recognition of its own comments is by text prefix, so someone who can comment can fake one and only delay or use up the reminders of that pull request. Reminders under `DRY_RUN` are only logged.

### Notifications

By default the human hears of a hand-over only through the forge: a comment that mentions `HUMAN_LOGIN` makes the forge send its own mail, with its own subject and layout, for every hand-over, reminder and mention. Notifications are a second path of ForgeHands' own: a short, plain message when a human is needed and cannot be avoided, plus an optional daily digest. Both are off until configured, and `HUMAN_MENTION=0` lets the forge keep quiet.

**How it looks.** Every message is a mail with a plain-text and an HTML part. The HTML has a short heading and, for the digest, one table per section (ticket, title, state) in which each ticket number is a link to its pull request, or to the issue when there is no pull request; an immediate message has a button to the pull request. Titles are escaped and cut, a leading `WIP:` is dropped, a link is only used when it is a plain `http(s)` address, and there is no script, image or external style. The plain text carries the same items with the link on the line below.

**What is sent.** _Immediate_ messages (`NOTIFY_IMMEDIATE`, one kind each):

| Kind       | When                                                                                                                                                                                                                                                                                                                                                            |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `handover` | A pull request is approved and green but touches a protected path: it waits for the human to merge. The message says what is done (reviewed, CI green, the security review OK, with CONCERNS or none), why a human is needed (the `reasons` text of `MERGE_POLICY` for the matching patterns, else "it touches protected paths"), how many files, and the link. |
| `blocked`  | A pull request or ticket got `BLOCKED_LABEL`: rounds used up, no verdict, an approval without a valid review, a dependency update a worker cannot fix.                                                                                                                                                                                                          |
| `conflict` | A conflict ForgeHands cannot resolve (no conflict route, or the pull request does not merge cleanly although approved).                                                                                                                                                                                                                                         |
| `failed`   | A run failed for good and was reported, or the merge itself failed.                                                                                                                                                                                                                                                                                             |
| `checks` | A repository has no CI: no workflow file and no check reports on the head of a pull request. Once per repository and process. Revert-on-red and verification cannot work without CI. Sent when `NOTIFY_IMMEDIATE` names it, like `failed`. See [Checks from the forge](#checks-from-the-forge). |
| `stalled` | Nothing has started for `STALL_ALERT_MINUTES` while work waits on a quota, the disk or a limit (never on a dependency chain), and no run is running: the counts of what holds the work. At most one in six hours. Sent when `NOTIFY_IMMEDIATE` names it, like `failed`. See [Status page and metrics](#status-page-and-metrics).
| `disk_full` | The filesystem of `WORKSPACE_CLEANUP_DIR` is at or above `DISK_WARN_PERCENT`: at most one message a day. Sent whenever a channel is configured; it does not need `NOTIFY_IMMEDIATE`. See [Cleaning the workspace](#cleaning-the-workspace).                                                                                                                                                                                                                                                                             |

A message is three to six short lines: the subject names the repository and number (`[homegraf] #140 waits for you to merge`), the body a cut title, the few facts above and the link in the `link` field (SMTP adds it as the last line). It never holds code, file names, file contents or ticket text beyond the title, cut at 80 characters and cleaned of control characters. `NOTIFY_LANGUAGE=de` writes the same in German (`[homegraf] #140 wartet auf deinen Merge`). Each message is sent from the same place as the comment that mentions the human; the comment itself is unchanged apart from the mention. With `NOTIFY_IMMEDIATE` empty (the default) nothing is sent.

**The digest** (`NOTIFY_DIGEST=08:00`, time of `NOTIFY_TIMEZONE`): once a day, in the first housekeeping pass after that time, one message lists what is for the human now: pull requests waiting for him with their age in days (the list `/status` shows as `waiting_for_human`, which the daily reminder pass fills, so it needs `REMIND_AFTER_DAYS`), blocked tickets (blocked, with no run since), tiers held back by a quota and when they are expected back, and runs that failed for good in the last 24 hours; one closing line says how many tickets merged in the last 24 hours. A line looks like `#140 ingressctl: resolve presets … (waiting 2 days)`; at most 15 items are listed, then "and N more". **If there is nothing for the human, no message is sent** (no "all fine" mail). The date of the last digest is kept in the ledger, so a restart neither sends the day's digest twice nor skips it (a process that was down at the time sends it when it is up again the same day).

**The follow-up figure** is a quality measure of the automatic merges, shown in a digest when one goes out (it never sends one by itself): `Follow-up fixes after automatic merges (7 days): N of M (x %)`. M counts the pull requests the agent user merged in the last 7 days, N those of them that a merged pull request of the same repository followed within 48 hours with a fix title (Conventional Commit type `fix`, `fix(scope):` too) that touches at least one of the same files. For N up to 5 the pairs follow as links (`fix #n fixes #m`). Who merged comes from the forge (`merged_by` of each pull request), not from the ledger, which misses merges. At most 120 forge calls per digest: the listing pages, one read per candidate pull request for `merged_by` (only branches `ai/issue-<n>` and the dependency bot branches and authors are asked), and the file reads. A read that fails leaves that pull request out and is logged. Limits, all approximations: the fix type is read from the title only (the first commit is not read), only the newest 250 updated closed pull requests of a repository are listed, a fix that is not in that list is missed, and a repository with more candidates than the 120 calls covers counts fewer of them (the log says when the budget ran out). Forgejo and Gitea answer `merged_by`; on GitLab the figure is skipped. A fix is not a planned follow-up: a ticket that depends on another one through issue dependencies is only counted when its title says `fix`.

**Set up SMTP.** For a mail server with a certificate that verifies:

```
SMTP_HOST=smtp.example.org
SMTP_PORT=587
SMTP_SECURITY=starttls
SMTP_USER=forgehands@example.org
SMTP_PASSWORD=...
SMTP_FROM=forgehands@example.org
SMTP_TO=maintainer@example.org
NOTIFY_IMMEDIATE=handover,blocked,failed
NOTIFY_DIGEST=08:00
NOTIFY_TIMEZONE=Europe/Berlin
HUMAN_MENTION=0
```

A **Proton Mail Bridge** on a LAN host listens on port 2025 (STARTTLS) with a self-signed certificate and a bridge-specific password. Either accept the certificate or, better, trust it by file:

```
SMTP_HOST=192.168.1.20
SMTP_PORT=2025
SMTP_SECURITY=starttls
SMTP_USER=you@proton.me
SMTP_PASSWORD=<the bridge password, not the account password>
SMTP_FROM=you@proton.me
SMTP_TO=you@proton.me
SMTP_TLS_VERIFY=0            # the Bridge's certificate is self-signed
# SMTP_CA_FILE=/run/secrets/bridge-cert.pem   # instead: keep verification on and trust this certificate
```

The client is built in (`node:net`, `node:tls`): `EHLO`, STARTTLS or implicit TLS or none, `AUTH PLAIN` with `AUTH LOGIN` as fallback, multi-line replies, timeouts (10 s to connect, 30 s per command). The message is `text/plain; charset=utf-8`, quoted-printable; a non-ASCII subject is an RFC 2047 encoded word. At start ForgeHands logs one line naming the channels, the immediate kinds and the digest time (never the password); `/status.json` has the same under `notify`. A send that fails is tried again after 1, 5 and 30 minutes, then logged and counted in `forgehands_notifications_total{channel,kind,result}` (`sent`, `failed`, `dry`); the retry queue lives in memory only, so a restart drops what was waiting. `notify` never blocks the loop or throws. Under `DRY_RUN` a notification is only logged, one line with the subject.

**`HUMAN_MENTION=0`** writes the hand-over, failure and reminder comments without the `@login` so that the forge sends no mail; the rest of each comment is identical, and the comment stays the record on the pull request. Use it together with `NOTIFY_IMMEDIATE`, otherwise the human hears of nothing.

**Other channels.** `NOTIFY_WEBHOOK_URL` posts `{"subject", "text", "link", "kind"}` as JSON (optional `Authorization` from `NOTIFY_WEBHOOK_AUTH`); ntfy, Telegram bridges and chat webhooks can be reached through it. A new channel is a class with `name` and `send(message)` in `src/notify/` (the `Channel` interface).

**Security notes.** Every header value and address is stripped of CR, LF and other control characters before use, so a title or an address cannot start a header or an SMTP command; addresses must match a plain pattern or the send is refused; the subject is cut at 200 characters. STARTTLS is required, never optional: a server that does not offer it is an error, not a reason to send the password in clear text (`SMTP_SECURITY=none` with a login is accepted only to localhost). Errors name neither the password nor the webhook URL and token. Messages are built from fixed strings and a few safe fields; ticket text appears only as a title cut at 80 characters. `SMTP_TLS_VERIFY=0` removes protection against a man in the middle on the way to the mail server: use it only on a trusted LAN, or prefer `SMTP_CA_FILE`. Notifications apply in direct mode only.

### Housekeeping

**The ledger sync** (`LEDGER_SYNC_HOURS`, default 6; `0` = off; first pass about a minute after the start). A close event can be missed (the ticket was closed by hand, merged before this was kept, or while ForgeHands was down), and the ledger then keeps the ticket open. Each pass reads the state in the forge of the tickets the ledger holds as not closed (issue tickets and dependency bot pull requests of `ALLOWED_REPOS`, not those with a run running, not in a dry run) and marks the closed issues and the closed or merged pull requests closed, as the close event would have. It makes at most 60 reads per pass, one per ticket, the ones checked longest ago first (the time of the last check is kept on the ticket's jobs), so a large ledger is worked off over several passes. A read that fails leaves the ticket as it is. Counted in `forgehands_ledger_sync_closed_total`. An issue whose own read answers 404 is counted, and it is marked **deleted in the forge** on the second pass that finds it missing (a single 404 can come from a proxy; a read that finds the issue again starts the count over, and a read that fails for another reason changes nothing). The mark is kept in the ledger, so a restart does not read it again. A deleted issue leaves the open list of the status page: its state is `deleted in the forge` and it is `closed` in `/status.json`. Its waiting and queued jobs are dropped, as `deleted`, and the jobs that waited for it are released from it. One log line, `<repo>#<n>: deleted in the forge, removed from the status page`, and no further reads of it. A pull request answering 404 drops the queued jobs that name it at once (`forgehands_deleted_tickets_total` counts both). A 404 of an issue's dependency list alone is not a deletion: the ticket's own read decides. It reads one ticket at a time rather than listing the repository's closed issues: the forge client has no issue listing, and 60 reads per pass cost less than the listing would per page. Forgejo and Gitea answer the same reads; GitLab too.

Finished runs archive themselves (`ARCHIVE_AFTER_DAYS`): about once an hour ForgeHands adds the tag `archived=true` (other tags stay, so runs can still be found by `source`, `issue`, `pr`, `ci`, `epic`) to conversations that ended long enough ago, at most 20 per round. Archived runs stay in the ledger until it prunes them (30 days).

**Deleting old conversations (`DELETE_AFTER_DAYS`).** Archiving does not free anything: OpenHands keeps every conversation on disk. After archiving, the same hourly pass can delete the conversation of an archived run that ended `DELETE_AFTER_DAYS` days ago, with `DELETE /api/conversations/{id}`. A failed run may keep its conversation longer (`DELETE_FAILED_AFTER_DAYS`). **What is lost:** the conversation in OpenHands, that is the trajectory and the events of the run, and with it what the agent did step by step. **What stays:** the ledger job with its state, result, cost, tokens and the ticket's history; the status page shows no conversation link for a deleted run; the token and cost metrics are unchanged. Nothing is deleted while a job of the same conversation is queued, waiting or running, or is not yet finished with it, or while an open ticket has a nudge or a resume pending. At most 40 conversations per round; a failed delete is retried on the next round, and a conversation that is gone already (404) counts as deleted. `DRY_RUN` deletes nothing. The counter `forgehands_conversations_deleted_total` counts the deletions, and each round logs `conversations: N deleted, M kept`.

## Cleaning the workspace

OpenHands runs every job in its own clone directory below its workspace (`WORKSPACE_DIR`, `/projects` in the OpenHands container), and nothing removes them. A clone of a repository with `node_modules` takes gigabytes, so a busy installation fills its disk. With `WORKSPACE_CLEANUP_DIR` set, ForgeHands removes the clones itself and keeps new runs from starting when the disk is nearly full. Off by default: nothing is deleted until the variable is set.

**Setup.** Mount the host directory that the OpenHands container uses as its workspace into the ForgeHands container as well, read-write, and point `WORKSPACE_CLEANUP_DIR` at the mount. The directory must be the same host directory the OpenHands container mounts as `WORKSPACE_DIR`, for example in the compose file of ForgeHands:

```yaml
services:
  forgehands:
    volumes:
      - /srv/docker/openhands/projects:/workspace
```

with `WORKSPACE_CLEANUP_DIR=/workspace`. ForgeHands cannot check that the two are the same directory; it only sees the names in it. The path must be absolute and must not be `/`, otherwise the start fails.

**Which directories go.** A pass runs every 30 minutes and once a minute after the start. A pass deletes:

- the clone of a job that ended, when every job that names that directory has ended and each of them ended longer ago than `WORKSPACE_KEEP_HOURS` (`WORKSPACE_KEEP_FAILED_HOURS` for a job that failed). A queued, waiting or running job keeps its directory, however old;
- an orphan: a directory that no ledger job names (runs from before this feature, or jobs the ledger pruned after 30 days), once its modification time is older than `WORKSPACE_ORPHAN_HOURS`.

The names are the ones ForgeHands gives its clones, computed by the same function as the prompt (`workspaceName` in `src/agent/prompt.ts`): `<owner>-<repo>-issue-<n>`, `-pr-<n>` for a dependency bot, `-epic-<n>`, with the suffixes `-round-`, `-review-`, `-fix-`, `-conflict-` and `-security-`. Nothing else in the directory is a candidate and nothing outside it is touched. Symbolic links are never followed: a link inside a clone is removed as a link, and its target stays.

Each deleted directory is logged (`<name>: cleaned (size not measured)`; the size is not walked, it would be expensive), with one summary line per pass. A delete that fails is logged and tried again in the next pass. `WORKSPACE_CLEANUP_DRY=1`, or `DRY_RUN=1`, logs `would be cleaned` instead and deletes nothing.

**Permissions.** The ForgeHands image runs as `node`. OpenHands writes its clones as root, and a user that does not own a directory may not delete what is in it. Such a delete fails, is logged and is tried again every pass, and the disk fills as before. Run the ForgeHands container as a user that may delete them (`user:` in the compose file), or make sure the directory is owned by that user.

**The disk guard** (`DISK_WARN_PERCENT`, `DISK_MIN_FREE_GB`) reads the filesystem of `WORKSPACE_CLEANUP_DIR` at every dispatch tick:

- at or above `DISK_WARN_PERCENT`, one `disk_full` notification a day through the channels (see [Notifications](#notifications)). It is kept in memory, so a restart may send it once more;
- below `DISK_MIN_FREE_GB`, no new run starts. The queued jobs wait, and the status page shows `queued: low disk space (<free> GB free)`. The hold starts a cleanup pass at once, and it ends as soon as the free space is above the limit again. Running runs are not touched, and nothing else is held back.

**Seeing it.** The status page and `/status.json` (field `workspace`) show the last pass, the directories it cleaned, the disk usage and the hold. The metrics are `forgehands_workspace_disk_used_percent` and `forgehands_workspace_disk_free_bytes` (gauges, only while the cleanup is on) and `forgehands_workspace_cleaned_total` (counter). The start logs the setting it runs with.

**Limits.** A round whose webhook carried no delivery id gets a time-based directory name that cannot be computed again; its directory is protected by its prefix while the job is active, and it is judged as an orphan afterwards. Webhook events always carry a delivery id, so this does not happen in practice.

## Status page and metrics

Both are direct mode only, read only and served by the same port as the webhook.

**Authentication.** With `STATUS_TOKEN` set (at least 16 characters), `/`, `/api/dashboard`, `/dashboard/ws`, `/status`, `/status.json` and `/metrics` answer `401` (with `WWW-Authenticate: Basic`, no ledger data) unless the request carries `Authorization: Bearer <token>` or HTTP basic auth with any user name and the token as password. An authorized browser response receives a signed, `HttpOnly`, `SameSite=Strict` session cookie (8 hours) so its WebSocket can authenticate without putting the token in a URL or client bundle. The comparison is constant time. Basic auth sends the token in base64: keep it behind TLS. `/healthz` stays open. Without `STATUS_TOKEN` the status endpoints are open and ForgeHands logs a warning at start; either way keep them behind the same internal reverse proxy as the webhook.

**`GET /`, `GET /api/dashboard`, `GET /dashboard/ws`.** The root serves a responsive React/Vite dashboard in direct mode. It summarizes live run capacity, repository outcomes, tiers and ticket activity; search, ticket filters (including a dedicated waiting-for-human filter) and 7/30-day windows are client-side. Ticket and pull-request references link to the forge when a safe web URL is available. `/api/dashboard` and the WebSocket carry the same read-only status model as `/status.json`; the socket sends an initial snapshot and a fresh snapshot every three seconds. The client reconnects with bounded backoff. The frontend is built to static files and adds no runtime dependencies. For local UI development, run the service in direct mode with `npm start`, then run `npm run ui:dev`; Vite serves port 5173 and proxies the dashboard API and WebSocket to port 8080.

**`GET /status`, `GET /status.json`.** The legacy status view and JSON remain available. Per issue (and per dependency bot pull request) they show what the ledger knows: runs with kind, state, result, conversation id, cost, the pull request number, the rounds used (`n/MAX_ROUNDS`, with "escalated to <label>" when the last round ran on the stronger route) and one line for the state (worker running, waiting for #n, waiting behind stuck #n (see [Stuck pull requests](#stuck-pull-requests-the-watchdog)), waiting behind epic with gaps #n (see [Epics that stay open after their review](#epics-that-stay-open-after-their-review)), epic review pending and waiting behind epic review pending #n, follow-up round, fix after red CI, review, security review, epic review, rounds used up, waiting for a human, failed). No event text but the issue title. The HTML refreshes itself every 30 seconds. Closed tickets whose last activity is older than `STATUS_HIDE_DAYS` (default 7) are left out of the list and counted in `hidden` in `/status.json`; the page then links to `?all=1`, which lists them too (`/status?all=1`, `/status.json?all=1`). The summary and the metrics are computed as before. `/status.json` also has `notify` (channels, immediate kinds, digest time; no secrets). A dry run shows a banner, and `/status.json` has `dry_run` with the repositories and the latest would-be writes.

**The summary** above the tickets (in `/status.json` under `summary`, per repository, for the last 7 and 30 days of the ledger):

| Column                 | Meaning                                                                                                                                                                                                                                                                            |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Merged (no human)      | Tickets merged in the window, and how many of them ForgeHands merged without ever calling a human (merged by ForgeHands and never blocked). A merge by a human is noticed when the push to the default branch closes the ticket, so it counts as merged, never as without a human. |
| Reverted merges        | Merges of the window whose revert pull request was merged, of the merges ForgeHands made (`revert_rate`: `merges`, `reverted`, `needed_human`, `ratio`). The definitions are in [The revert rate](#safety-nets-for-merges-without-a-human). |
| Blocked                | Tickets that got `BLOCKED_LABEL` (an unreviewed approval, used-up rounds, a failed run, ...).                                                                                                                                                                                      |
| Split                  | Tickets sent to the planner by `SPLIT_LABEL`.                                                                                                                                                                                                                                      |
| Median / p90 to merge  | Time from the ticket's first run to its merge.                                                                                                                                                                                                                                     |
| Rounds per merged      | Follow-up rounds per merged ticket.                                                                                                                                                                                                                                                |
| Review / error retries | Review runs started again for a missing verdict, and runs restarted after `error`, over the runs created in the window.                                                                                                                                                            |
| Cost                   | Sum of the runs' cost in the window.                                                                                                                                                                                                                                               |

**Runs per tier.** Under each repository's entry in `summary`, `tiers` has one object per tier (the `tier` of the routes) with `last_7_days` and `last_30_days`, and the page shows them as a table under the summary. Each tier object also has `tokens`, `{prompt, completion, cache_read}`: the sums over the runs of that tier that started in the last 7 days. OpenHands reports the cost of the gateway models as 0, so the tokens are the figure to watch; the counter `forgehands_tokens_total` has the same numbers by repository, tier and route kind. A run counts for the tier it really ran on: the fallback route of `fallback_to` or the `escalate_to` target of an escalated round. Per window (by the start of the run): `started`, `finished`, `failed` by reason (`max_iterations`, `error`, `stuck`, `timeout`, `no_delivery`, `other`), `split` (tickets sent to `SPLIT_LABEL`, counted for the tier of the run that was split), `fell_back`, `escalated`, and `merged_share`, the share of finished worker runs (`worker_runs_merged` of `worker_runs_finished`) whose ticket has a merged pull request so far (`null` without finished worker runs). It shows whether a cheap model pays off. Tiers without a run in 30 days are left out.

**Closed tickets.** When ForgeHands learns that an issue is closed (the `issues closed` event, or `closeMergedTickets`), it marks the ledger jobs of the issue (`archived_view`, kept in the ledger; runs that are still queued or running are not marked). Such an issue is listed in a collapsed "Closed" section of the page and has `closed: true` and state `closed` in `/status.json`; it never appears in `waiting_for_human` and never as "rounds used up" or failed. At start and then once a day, in the hourly housekeeping pass, ForgeHands reads the issues of tickets with a failed run, used-up rounds or a waiting job from the forge (at most 20 per pass, the rest in the next pass) and marks those the forge reports closed; a failed read changes nothing. The counts of the summary do not change.

**Factory health (`factory` in `/status.json`).** The dashboard's Factory health area reads this section (`src/server/factory.ts`), next to the waiting list at the top of the page. `stalled_tickets`: `count` (handed to a human), `actions` (`restart`, `human`), and `list` of the open tickets the ticket watchdog acted on, with `action`, `restarts`, `run` and `since`. `stuck_pull_requests`: `count` and `list` of the blocked pull requests (`pr`, `reason`, `since`), and `blocks` by reason. `merge_decisions`: `open` gives the last refusal of each open ticket's pull request (`reason`, `at`), and `counts` the merges and the refusals by reason. `handbacks` counts retry, escalate, planner and blocked. `preflight` has `results` (ok, rejected, advised, skipped), `rules` (rule and result) and `notes`, the advisory notes of the open tickets the pre-flight checked (the last 100, kept in memory). `epic_gaps`: `count`, `actions` (replanned, handed) and `list`. `deleted_in_forge` counts the tickets deleted in the forge, which the dashboard leaves out of its ticket list. `revert_rate.alert_percent` is `REVERT_RATE_ALERT` (`null` when off); the rates per repository and window are in `summary`. The lists come from the ledger. The counts by action, kind, reason or result are the counters of `/metrics`, so they count from `since` (the start of the process), not from the ledger's 30 days. `waiting_for_human` reasons are shown as words, and a reason the dashboard does not know is shown as its words too. `epic_reviews` lists the epics whose review is pending (all sub-issues closed, no review since; see [Epics that stay open after their review](#epics-that-stay-open-after-their-review)).

**Why queued work waits.** A dispatch pass in which something waits and nothing could start logs one line (a dependency cycle adds `<k> in a dependency cycle`; its tickets are named on /status.json and in the stall notification): `idle: <n> waiting: <a> on dependencies, <b> on files of older tickets, <c> held (quota <tiers>), <d> held (low disk), <e> over the hourly limit, <f> over a concurrency limit`; a wait behind a blocked pull request adds `<k> behind a blocked pull request` (see [Stuck pull requests](#stuck-pull-requests-the-watchdog)). Each waiting job is counted once, for the first reason that holds it: an issue that depends on open issues (and a CI result kept while its run goes on) is a dependency wait; a ticket with the same files as an older one is a files wait; a queued job is held by the first check that fails, in this order: low disk, the global concurrency (`MAX_CONCURRENT`), the quota hold of its tier (the tiers are named), the concurrency of its tier (`MAX_CONCURRENT_PER_TIER`), the hourly limit (`MAX_RUNS_PER_HOUR`). A queued job whose retry timer has not run out is not counted. The line is logged when its composition changes, and at most every 15 minutes otherwise. `/status.json` has `idle: {since, reasons: {dependencies, files, quota, disk, hourly, concurrency, could_start, cycle, stuck}, quota_tiers}` while such a pass is the last one, and the gauge `forgehands_idle_jobs{reason}` has the same numbers. `could_start` counts queued jobs that could start and did not; it is 0 in normal operation.

**The stall alert (`STALL_ALERT_MINUTES`, default 90, `0` = off).** When work waits on a quota, the disk or a limit (not on a dependency: a chain of tickets is normal), no run is running and nothing has started for that many minutes, one `stalled` notification goes out with the counts of the holds. It is not repeated for six hours, unless nothing waits any more. It is sent like `failed`: it reaches the human when `NOTIFY_IMMEDIATE` names `stalled`. The quiet time counts from the last start of this process, so a restart begins the count again.

**Links to the forge.** Every issue and pull request the status shows links to it in a new tab: the tickets, the stalled, stuck and merge-decision lists, the epic gaps, the operator tickets, the pre-flight notes, the waiting-for-a-human list, and the `#n` numbers in state lines (`waiting for #54, #55`, `delivered as a comment on #n`, `waiting behind stuck #n`). The server builds the addresses (`src/server/forge-links.ts`) from `FORGE_URL` and the repository: `/issues/<n>` and `/pulls/<n>` on Forgejo and Gitea, `/-/issues/<n>` and `/-/merge_requests/<n>` on GitLab. The fields are additive in `/status.json`: `issue_url` and `pr_url` on tickets and on each list entry, `state_links` (number to address) on a ticket, `reason_links` and `notes_links` on the entries that carry free text. Without `FORGE_URL` and `FORGE_TOKEN` there are no addresses and the numbers stay plain text.

**`GET /metrics`.** Prometheus text format, written by hand, no dependency. Gauges from the ledger, read at scrape time: `forgehands_jobs{status,kind}`, `forgehands_jobs_waiting`, `forgehands_queued_jobs{repository}`, `forgehands_tier_cooldown_active{tier}`, `forgehands_idle_jobs{reason}` (the queued and waiting jobs by what holds them back, see below, `cycle` and `stuck` included; `forgehands_stuck_pull_requests` (the blocked agent pull requests, see [Stuck pull requests](#stuck-pull-requests-the-watchdog)); 0 while nothing waits), `forgehands_merges_reverted_ratio{repository}` (the revert rate of the last 30 days, 0 to 1, absent without merges in the window, see [The revert rate](#safety-nets-for-merges-without-a-human)), and with `WORKSPACE_CLEANUP_DIR` `forgehands_workspace_disk_used_percent` and `forgehands_workspace_disk_free_bytes`. Counters since start (in memory, they reset on restart): `forgehands_ledger_sync_closed_total` (tickets the ledger sync marked closed), `forgehands_webhook_deliveries_total{event,result}` (result `accepted`, `ignored`, `duplicate`, `rejected_signature` or `failed`), `forgehands_runs_started_total{kind}`, `forgehands_runs_finished_total{kind,state}`, `forgehands_merges_total{repository}`, `forgehands_merge_refusals_total{reason}` (`protected_paths`, `no_valid_review`, `ci_not_green`, `not_mergeable`, `blocked`, `held_label`, `merge_failed`), `forgehands_merge_decisions_total{result,reason}` (every decision on an approved pull request: `result` `merged` or `not_merged`, the reason of a refusal, see [Auto-merge](#auto-merge)), `forgehands_blocks_total{reason}`, `forgehands_error_retries_total`, `forgehands_branch_updates_total`, `forgehands_branch_conflicts_total`, `forgehands_openhands_api_errors_total{class}`, `forgehands_forgejo_api_errors_total{class}` (the forge's API errors, whichever forge; class `network`, `4xx` or `5xx`), `forgehands_escalated_rounds_total`, `forgehands_tier_runs_total{repository,tier,result}` (ended runs by the tier they really ran on; result `finished`, `max_iterations`, `error`, `stuck`, `timeout`, `no_delivery` or `other`; a worker run that finished without delivering counts as `finished` and again as `no_delivery`), `forgehands_reminders_total`, `forgehands_notifications_total{channel,kind,result}` (`sent`, `failed` or `dry`), `forgehands_comment_restarts_total`, `forgehands_comment_ignored_total{reason}` (answers of the human to a finished planner that started nothing), `forgehands_resumes_total{kind,state}` (`state` `stuck` or `timeout`), `forgehands_failure_escalations_total`, `forgehands_nudges_total{kind}`, `forgehands_wait_cycles_broken_total` (same-files waits not taken because they would close a cycle), `forgehands_stuck_pr_blocks_total{reason}` (pull requests the watchdog blocked, `stuck_rounds` or `stuck_verdict`), `forgehands_tokens_total{repository,tier,kind,type}` (the tokens of a run, added up when its conversation ends; types `prompt`, `completion`, `cache_read`, `reasoning`), `forgehands_dry_run_writes_total`, `forgehands_workspace_cleaned_total`, `forgehands_merges_reverted_total{repository}` (merges whose revert was merged, once per merge), `forgehands_reverts_needing_human_total{repository}`, `forgehands_preflight_total{result,rule}` (the ticket pre-flight: `ok`, `skipped`, `rejected` or `advised`, a rejection or an advisory finding by rule `1` to `4`, see [the ticket pre-flight](#a-ticket-is-checked-before-a-worker-starts)); and the histogram `forgehands_run_duration_seconds{kind}`. Labels come from known sets only (repositories of `ALLOWED_REPOS`, route kinds, tiers, fixed reasons), never issue numbers. A 404 from OpenHands is not counted as an error (a deleted conversation is a normal answer).

    metrics_path: /metrics

      credentials_file: /etc/prometheus/forgehands-token # the STATUS_TOKEN

## End-to-end suite

After each deploy (`E2E_ON_START=1`) or on demand (`POST /e2e/run` with `Authorization: Bearer <STATUS_TOKEN>`; without `STATUS_TOKEN` the endpoint answers `403`), ForgeHands runs scenarios against a test repository: a ticket gets its run, the pull request is reviewed and merged, and a change that turns the default branch red is reverted, reopened and started again once. Each scenario cleans up after itself (tickets, pull requests, the queued runs of its tickets, branches, the default branch); the runs still going are waited for. A wait for a run counts from the start of the run, and a queued one has `E2E_QUEUE_MINUTES`. A failed scenario sends a notification of kind `failed` (`NOTIFY_IMMEDIATE`), and `forgehands_e2e_scenario_ok{scenario}` and the status page show the result. The scenarios' tickets must pass the ticket pre-flight. The test repository must be dedicated to this: see [docs/e2e.md](docs/e2e.md) for its setup, the CI step, the scenarios and their preconditions. Forgejo and Gitea only.

## Dry run

`DRY_RUN=1` receives and judges events as usual and changes nothing. Use it to try a new setup, a new route table or a new forge against real repositories, and to develop locally.

- **Judged as usual:** scheduling, limits, dependencies, the merge policy, the verdict check. `/status` shows what would start, wait or merge.
- **Only logged:** every write to the forge (comments, labels, reviews, merge, branch update, title change, issue close) as `DRY RUN, not sent: <method> <repository>/<path> <body>`, every OpenHands call that is not a read, and in webhook mode the forward. A job that would start ends as status `dry` with the first message it would have sent kept in the ledger as `dry_prompt`; it holds no slot. Reads stay real, with the real tokens.
- **Narrowing it:** `DRY_RUN_REPOS=owner/repo,...` makes only those repositories dry and leaves the others live. Every entry must be in `ALLOWED_REPOS`, and it is an error without `DRY_RUN=1` (it would otherwise run live without a word). `DRY_RUN` takes `1` or `0`, nothing else.
- **Seeing it:** a warning at start, a banner on `/status`, `dry_run` in `/status.json` (repositories and the latest 200 would-be writes, in memory), and the counter `forgehands_dry_run_writes_total`.
- **Limits:** the dry job finishes at once, so concurrency over a run's duration is not simulated, and what depends on a write (a label that stays, an issue that closes) does not happen, so later events see the unchanged forge. The request body to OpenHands (it carries `AGENT_SECRETS`) is never logged, but `/status.json` shows up to 300 characters of would-be comment bodies: keep it behind `STATUS_TOKEN` or a proxy.

## Security and limitations

See [SECURITY.md](SECURITY.md) for the trust model in full.

- Issue, pull request and comment text is untrusted. ForgeHands never fetches repository URLs from events. In direct mode it holds the secrets named in `AGENT_SECRETS` and the backend key and hands them to the agents; keep `OPENHANDS_API_KEY` and the forge tokens out of the repository and give them to the container through its secret store.
- Restrict public access, use TLS termination, keep secrets out of logs and restrict outbound networking to your OpenHands and forge.
- A GitLab webhook with a signing token (`whsec_...`) is checked by HMAC like Forgejo and Gitea. With a plain secret token it is authenticated by a shared token in clear, which is weaker; see GitLab setup.
- `STATUS_TOKEN` protects the status page and metrics; without it they are open.
- The delivery store and the ledger are local JSON files: **single instance only**. Use a shared atomic database before scaling out.
- Retries rely on the forge's retries or a manual redelivery. A failure after OpenHands accepted a webhook-mode request but before ForgeHands recorded it can cause a duplicate; configure OpenHands's `event_id_header` for defense in depth. There is no durable outgoing queue in webhook mode: if OpenHands is down the answer is HTTP 502.

## Stability and versioning

ForgeHands follows [semantic versioning](https://semver.org). Until 1.0.0 a minor release (0.x.0) may change behaviour; [docs/UPGRADING.md](docs/UPGRADING.md) says what changed and how to keep the old way where there is one. From 1.0.0 on, the interface below changes only in a major release.

**Covered:**

- **Environment variables.** Their names, defaults and meaning, as documented in [Configuration](#configuration). A new variable can come in a minor release. If it changes behaviour, it starts out off, or its default is the behaviour from before.
- **The ledger file** (`jobs.json`). A release reads every ledger written since 0.2.5 (`version` 2 and later), migrating it on load (`LEDGER_VERSION`). A ledger written by a newer release stops the start instead of being read with parts lost.
- **Webhook paths and the signatures checked on them**: `/webhooks/forgejo`, `/webhooks/gitea` and `/webhooks/gitlab`.
- **What ForgeHands writes to the forge that people and tools act on**: the labels it sets or reads (`APPROVED_LABEL`, `BLOCKED_LABEL`, `HOLD_LABEL`, the route labels), the branch names (`ai/issue-<n>`, `ai/revert-<n>`), and the verdict lines a review must carry (`Verdict: OK|NOT OK`, `## Security review: OK|CONCERNS`).
- **Observability**: the metric names and their labels on `/metrics`, and the fields of `/status.json`.

**Not covered:**

- **Wording** of comments, prompts, log lines and the HTML of the status page.
- **The end-to-end suite** (`E2E_*`), which is operations tooling.
- **The source code** under `src/`. ForgeHands is a service, not a library.

**Deprecation.** A variable that is renamed or removed in a minor release keeps working, or is ignored, with a warning at start for at least one further minor release. It is then dropped only in the next major release. `TIER_WEEKLY_BUDGETS` went this way.

`test/interface.test.ts` pins the variables (each must be documented here and in `.env.example`), the metric names, the webhook paths and the ledger version. A change that touches them fails that test and has to update it on purpose.
